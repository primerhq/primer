---
title: "Not agent-callable yet"
summary: "Features only the console and REST can drive today, and what an agent can do instead."
order: 160
---

Some features have no agent tools yet. Each entry says what the feature is, how a person drives it today, and what you can do instead.

- **Speech:** Speech-to-text and text-to-speech: the provider rows, the active speech config and the audio endpoints. A person drives them from the console, or over `GET` and `POST /v1/stt_providers`, `GET` and `POST /v1/tts_providers`, `GET` and `PUT /v1/speech_active_config`, and the audio endpoints under `/v1/audio/`. Voice is an edge transform: an agent stays text in and text out. An agent can set `tts_voice` on its own agent row.
- **Services:** Custom services and their versions. A person drives them from the console, or over `GET` and `POST /v1/services`, `GET` and `POST /v1/services/{service_id}/versions`, and `POST /v1/services/{service_id}/_activate` to activate or roll back a published version. There is no agent tool.
- **Users, API tokens and login:** The user rows, the API tokens and the login flows. A person drives them from the console, or over `GET` and `POST /v1/admin/users`, `GET` and `POST /v1/auth/tokens`, `GET /v1/admin/users/{user_id}/tokens`, and `POST /v1/auth/register`, `POST /v1/auth/login` and `POST /v1/auth/change-password`. Minting a token is a person's act by design: it needs a cookie session, and a bearer token cannot mint. An agent that needs a token asks the person to mint one.
- **Single sign-on:** The OIDC provider rows and the SSO settings. A person drives them from the console, or over `GET` and `POST /v1/admin/oidc-providers`, `GET` and `PUT /v1/admin/sso-settings`, and the `/v1/auth/sso/` routes that carry a browser through the provider. The SSO flow signs a person into the console; there is no agent tool for it.
- **MCP exposure:** Which of primer's tools outside MCP clients may call. A person drives it from the console, or over `GET` and `PUT /v1/mcp_exposure`; the outside client's endpoint is `POST /v1/mcp`. Pausing tools and tools with a `required` approval policy are never exposed. An agent in a session calls its granted tools directly.
- **Event subscriptions:** Standing subscriptions on the event log: rows that match events in the log and sink them. A person drives them from the console, or over `GET` and `POST /v1/event_subscriptions`. Instead: `system__wait_for_event` for one wait, or a trigger subscription for standing work.
- **Web search and fetch:** The provider rows behind the web tools. A person drives them from the console, or over `GET` and `POST /v1/web_search_providers` and `GET` and `POST /v1/web_fetch_providers`, with the active config over `GET` and `PUT /v1/web_search_active_config` and `GET` and `PUT /v1/web_fetch_active_config`. Instead: the web tools at [web search and fetch](web/search-and-fetch), and, for an admin, the active-config tools at [web search and fetch settings](providers/web-search-and-fetch).
- **Workers:** The worker pool: the processes that pick up claims. A person drives it from the console, or over `GET /v1/workers`, `POST /v1/workers/{worker_id}/drain` and `POST /v1/workers/purge_dead`. It is an operator task; there is no agent tool.
- **Deciding a gate:** Approving or rejecting a tool approval and answering an `ask_user`. A person decides from the console (or, when the policy allows, from the bound channel), or over `POST /v1/sessions/{session_id}/tool_approval/respond`, `POST /v1/sessions/{session_id}/ask_user/respond`, and `POST /v1/sessions/{session_id}/yields/{tool_call_id}/cancel` to cancel a parked yield. A person decides: an agent cannot approve its own gate, and a peer message is never an answer.
- **Manual compaction:** Compacting a session's transcript on demand, at `POST /v1/workspaces/{workspace_id}/sessions/{session_id}/compact`. A person drives it from the console; there is no agent tool.
- **The internal-collections subsystem:** Opt-in indexing of primer's own rows into collections. A person configures it from the console, or over the `/v1/internal_collections/` routes (the config and the bootstrap). This wiki does not depend on it.
- **Inbound webhooks:** `POST /v1/webhooks/{token}` is called by outside systems, not by primer. An agent makes the trigger at [triggers](triggers/triggers), but only the trigger's owner or an admin sees the token; list and get show it masked to everyone else.
- **Secrets:** Secret values are write-only fields inside provider, toolset and template rows. A GET serves them masked, and a PUT that sends the mask back keeps the stored value. There is no secrets tool, and an agent cannot read a secret back.
- **MCP sign-in:** Signing an OAuth MCP toolset in is an interactive browser flow. A person does it from the console at [MCP toolsets](toolsets/mcp-toolsets). An agent can read the state with `system__get_toolset_auth_status`; it cannot sign in.

How to ask a person: say what you need and which console page (or REST route) it lives in, and use `system__ask_user` at [ask the user](human-in-the-loop/ask-user).
