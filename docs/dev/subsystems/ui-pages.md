# UI Pages

## 1. Purpose

This doc covers the operator console: the pure shell modules under `ui/foundation/shell-*.js`, the three-view console under `ui/components/console/nv-*.jsx` (plus the two `ui/components/shell/` survivors, `sh-api.jsx` and `sh-activity.jsx`), and the page components under `ui/components/` that it hosts. The console IS the studio. There is no page router, no sidebar and no per-page chrome: one workspace-scoped surface, whose navigation is a verb registry, whose documents are deep-linkable tabs, and whose management surfaces are overlays re-hosting the page components unchanged.

It owns the shell's own model (the URL grammar, the tab semantics, the verb registry, the dual-render rule) and the repeating page shapes those overlays still use: the list-bar plus detail-tabs structure on CRUD entities, the find-bar plus table plus create-modal triad, and the loader/error/empty/confirmation conventions every page reuses.

It deliberately does not re-document the primitives these surfaces build on. The HTTP client, the polled `useResource` cache, optimistic `useMutation`, the router shim, the toast queue, the tweaks store, the idle and viewport hooks, and the shared widgets (`Modal`, `Banner`, `Btn`, `Icon`, `StatusPill`, `CardList`, `Fab`, `BottomSheet`, `MobileTabs`) all live in [ui-foundation.md](ui-foundation.md). The load-bearing rule from the foundation (route all I/O through the hook layer, never `apiFetch` directly) is assumed throughout.

The backend REST contract these pages consume (the `/v1/*` CRUD surface, the `make_crud_router` family, RFC 7807 ProblemDetails, the reserved-id and cascade-conflict semantics) is documented in [architecture/rest-api.md](../architecture/rest-api.md). Pages are the UI half of that contract; where a page surfaces a documented anomaly (T0025, T0379, T0711, and similar) the page-level affordance is described here and the backend cause in the relevant subsystem doc.

## 2. Conceptual model

The console is three views over one URL (the 2026-08-23 designer handoff): STUDIO (the default - a rail of session bands and files, a centre of document tabs, the composer, an optional terminal panel and events sidebar), PLATFORM (grouped nav over per-entity card pages), and SYSTEM (dashboard, users, API keys, SSO, MCP, internal collections, activity, profile - reached from the profile menu). Overlays open above whichever view is active, and a command palette reaches every verb. `ui/app.jsx` is one mount, `AuthGate` wrapping `NV_Shell`, and nothing else.

**The verb registry is the routing table.** Every action a user can take is registered once, with an id, a label, the contexts it applies to and the surfaces it renders on (rail, tab menu, palette, overlay button). A surface renders the verbs the registry gives it rather than hard-coding buttons, which is what makes the dual-render rule checkable: a verb declared for a surface but never rendered from the registry, or a doc kind the URL can address that no verb opens, is an orphan, and a static guard fails on it.

**A document is a tab, and a tab is addressable.** Sessions, files, diffs and wiki pages are the four doc kinds (the trace opens as a split INSIDE the session doc; attention lives in the bands and the System dashboard). Tabs follow VS Code semantics: a preview tab is replaced by the next preview and is promoted to permanent by an edit or a pin, so browsing a file tree does not accumulate tabs.

**A management surface is an overlay, not a page.** The catalogue, agents, graphs, collections, toolsets and the rest re-host their existing page components with no chrome around them. Comparison never goes in an overlay: a trace opens beside its transcript as a tab in a second group, because an overlay cannot be looked at next to anything.

Components attach themselves to `window` at module scope rather than being imported, because the bundle shares one global Babel scope; this is also why several pages prefix every top-level binding (workspaces uses `WS_`, triggers `TR_`, internal-collections `IC_`, agents `AG_`, graphs `GR_`, channels its own helpers) to avoid colliding with siblings in that scope.

The page anatomies below still hold, because the overlays host those same components.

Almost every entity surface follows one of two anatomies.

A list page is a find-bar (text filter plus entity-specific dropdowns or status chips), a desktop table (with a mobile `CardList` plus `Fab` fallback under `useViewport().isMobile`), and a create modal launched from a "New X" button. Filtering, sorting, and pagination are overwhelmingly client-side over a single `GET /v1/<plural>?limit=200` page; the poll pauses while the filter input is focused so typing is not interrupted.

A detail page is a header (breadcrumb, id, action buttons such as Edit / Delete / Invalidate / Back) over a tab strip whose active tab is carried in the URL as `?tab=` and read back through the router. The create modal is reused in edit mode: the same component takes an `existing` prop, locks the id (and often the type discriminator), pre-fills the form, blanks any masked-secret field so the redaction is never written back, and submits a `PUT`-replace instead of a `POST`.

```mermaid

    subgraph ListPage["List page anatomy"]
        FB["find-bar: text filter + chips/selects"] --> TBL["table (desktop) / CardList+Fab (mobile)"]
        TBL -->|row click -> navigate(/x/:id)| DET
        FB -.->|New X button| CM["create modal"]
    end
    subgraph DetailPage["Detail page anatomy"]
        DET["header: crumb + id + Edit/Delete/Back"] --> TABS["tab strip (?tab= in URL)"]
        TABS --> T1["Overview/Config"]
        TABS --> T2["entity tabs (Tools/Sessions/Messages/State/Files/Turn log/...)"]
        DET -.->|Edit button| CM
        DET -.->|Delete button| CONF["confirm modal (+ inline 409 banner)"]
    end
    CM -.->|POST/PUT then invalidate| TBL
```

A handful of surfaces break the mould: the System dashboard is a read-only metric board, the graph detail page is a drag-and-drop canvas editor rather than a tab strip, the internal-collections page is a three-state activation machine, and the docs page is a markdown reader. These are noted individually in the page index.

## 3. Architecture patterns implemented

- **The URL is the state.** Four facts are addressable and nothing else is: the workspace, the open document, the open overlay, and an anchor within the document. Palette state, toasts and every other transient are deliberately not representable, so a pasted link restores exactly what the sender was looking at and nothing they were not.

- **Registry-rendered surfaces, checked by the dual-render rule.** Verbs are registered once and each surface renders what the registry hands it. Two static guards enforce the consequences: every declared surface must actually render from the registry, and every addressable doc kind and overlay must be reachable by some verb. An address no verb reaches is a surface the user cannot find; a verb no surface renders is a promise the console does not keep.

- **Overlays re-host page components with no chrome and props only.** An overlay mount passes the component its own props and nothing else. Where a re-hosted page still calls `window.primerApi.useRouter()`, the shim answers from overlay state; see [ui-foundation.md](ui-foundation.md).

- **Every page builds on the foundation hook layer, never on raw fetch.** List polls, detail polls, modal submits, and confirmation deletes all go through `useResource` and `useMutation` on `window.primerApi`; cache keys are page-scoped strings (`sessions:list`, `session-detail:{sid}`, `graph-status:{id}`, `workspace-files:{wid}:{path}`, and so on) so a mutation on one surface can invalidate exactly the keys that need refetching. See [ui-foundation.md](ui-foundation.md) for the hook contracts and cache-key conventions.

- **List-bar plus detail-tabs is the default CRUD shape.** A `GET /v1/<plural>?limit=200` list with client-side filter/sort/paginate, a row-click navigation to `/<plural>/:id`, and a tabbed detail page whose tab lives in `?tab=`. Agents, toolsets, providers, semantic-search, channels, triggers, workspaces, collections, and graphs all instantiate this shape with entity-specific tabs.

- **Find-bar plus table plus create-modal triad.** The list bar exposes a text filter plus dropdowns or status chips; the create modal doubles as the edit modal via an `existing` prop and a `POST`-versus-`PUT`-replace switch. `PUT`-replace is the wire shape because the backend `make_crud_router` is full-replace, not PATCH.

- **Reuse-create-modal-for-edit with secret blanking.** Providers, channel-providers, semantic-search, and toolsets all pre-fill the create modal on edit, lock the id and type discriminator, and blank any field still holding the `**********` redaction so the stored secret survives. This mirrors the backend `SecretStr`-on-read masking documented in [architecture/rest-api.md](../architecture/rest-api.md).

- **Optimistic-write only for reversible edits; wait-for-200 for destructive or cascading mutations.** Description / metadata / config edits use the optimistic `useMutation` path; graph `PUT`-replace, workspace destroy, provider invalidate, and any delete wait for the response before refetching. The rationale lives in [ui-foundation.md](ui-foundation.md).

- **Anomaly surfaces are rendered in place, not hidden.** Documented backend quirks get a labelled banner or helper line on the owning page: T0025 model-list-is-static helper text in the embedding/cross-encoder provider and collection modals (the LLM provider form has no model list at all now -- see below), T0379 provider/config-not-cross-validated warning, T0711 MCP-HTTP 500 banner on the toolsets and agents Tools tabs, T0245/U0014 stdio-allowlist warning in the toolset modal. The backend cause is documented in the matching subsystem doc; the affordance is documented here.

- **Inline-for-input-validation, toast-for-action-outcome.** 422 ProblemDetails responses map `extensions.errors[].loc` to per-field inline errors in modals; non-422 failures and success acknowledgements go through the toast queue. Yielding-tool inputs (AskUser) render their 422/500 inline under the input rather than as a toast.

## 4. Code layout

The shell is split by testability. Pure logic lives in `ui/foundation/shell-*.js` as plain functions with no React and no DOM, so `tests/ui` can execute it in MiniRacer:

- `shell-url.js` - the URL grammar: `SH_parseUrl` / `SH_buildUrl`, `SH_DOC_KINDS`, `SH_OVERLAYS`, anchor parsing.
- `shell-verbs.js` - the verb registry, label lint and ranking.
- `shell-docs.js` - the tab model: open, pin, preview promotion, groups.
- `shell-status.js`, `shell-turns.js` - the status line and the transcript's turn folding.
- `shell-attention.js` - pending yields and approval records to attention items, tiered by consequence.
- `shell-router-shim.js` - `useRouter` over overlay state (see [ui-foundation.md](ui-foundation.md)).

The React surfaces live in `ui/components/console/nv-*.jsx` (the three-view flag day deleted the `sh-*` shell): `nv-shell.jsx` (the root: URL sync, the verb registry and chord dispatcher, the toast and confirm hosts), `nv-chrome.jsx` (activity bar + topbar: workspace menu with settings, search field, panel toggles, profile menu, and the theme helpers that menu, the phone's More tab and the theme palette verbs share), `nv-palette.jsx`, `nv-studio.jsx` (the studio frame and the pure band sort), `nv-sessions-sidebar.jsx` and `nv-files-sidebar.jsx`, `nv-doc-host.jsx`, `nv-session-doc.jsx` (transcript, binding chip, decision/ask cards, inline artifacts, trace split, composer, voice), `nv-file-docs.jsx`, `nv-terminal.jsx`, `nv-events-sidebar.jsx`, `nv-client-tools.jsx`, `nv-overlays.jsx` (the designer create panels plus the management-surface mount table), `nv-platform.jsx` and `nv-system.jsx`. Two shell-directory files survive: `sh-activity.jsx` (the events console the System view re-hosts) and **`sh-api.jsx`, the only file that names a URL**, so the endpoints the console depends on are enumerable in one place.

**A Platform form row names its control (console review C-003, beyond the auth forms).** `WS_FieldRow` (`ui/components/workspaces/shared.jsx`: the workspace provider and template forms) and `FieldRow` (`semantic-search.jsx`: the semantic-search provider forms) drew `<label class="field-label">` as a SIBLING of the input, with no `htmlFor` and no `id`, so a screen reader met unnamed edit fields and clicking a label focused nothing (72 fields). `FF_fieldControls` (`ui/components/shared/form-field.jsx`, inside `FormField`) gives the first native control among the row's direct children (`input`, `select`, `textarea`; its own `id` when it has one, else a `useId`-based one) the id the label points at, and an error (`err`) is `role="alert"` and tied to that control (`aria-invalid`, `aria-describedby`, merged with one it already has). A row whose control is a custom component or sits in a wrapper cannot be labelled by id, so the row is a `role="group"` named by its label (`aria-labelledby`). Only the first control of a row is labelled: a row with two inputs names the first. NOT done: the second control of a multi-control row (the hand-written `<label className="field-label">` sites elsewhere have the same defect and are counted by the ratchet in the next paragraph). (`tests/ui/test_form_rows_label_their_control.py` runs both components in V8, `tests/ui_e2e/test_form_rows_label_journey.py` the real template form.)

**One labelled form row, and a ratchet on the labels that name nothing (console review C-003, the rest of the console).** `FormField` (`ui/components/shared/form-field.jsx`; props `label`, `hint`, `help`, `err`, children, and `className`, `labelClassName`, `hintClassName` for a surface with its own look) is the console's one labelled row: `WS_FieldRow`, `FieldRow` and the console overlays' `NV_Field` are one-line wrappers of it, so the rule in the paragraph above has a single implementation, and a form draws `<FormField label="Name"><input /></FormField>` instead of a `<div className="field">` holding a bare label. The hand-drawn `<label className="field-label">` without `htmlFor` that remain are counted per file by `scripts/audit_field_labels.py` (a label that wraps its checkbox or input names it implicitly and is not counted; a comment that starts a line is skipped), and `tests/ui/test_field_label_ratchet.py` holds the count against `tests/ui/field_label_baseline.json`: a file may not have MORE than its baseline (a new bare label fails: use `FormField`) and may not have FEWER either, so the baseline is lowered with the conversion (`uv run python scripts/audit_field_labels.py --write`) and the gain cannot be given back later by a new bare label in the same file. The baseline started at 100 labels in 17 files (graphs 25, the harness form 11, workspaces 10, approvals 9, channels 8, the new-session form 7, internal collections 6, toolsets 6, then the rest); each surface converts in its own change and lowers its number. The scan also counts a `<div>` or `<span>` whose `className` literal carries `field-label` or `nv-field-label` (an element only styled as a label names nothing; the overlays' `NV_Field` was one and hid from the first version of the count), which adds 6 (workspaces 2: two block headings; agents 4: read-only value captions in the agent summary, which want a definition list rather than a field), so the baseline began at 105 in 17 files after the overlay fix and the graph-input row (each conversion PR lowers `tests/ui/field_label_baseline.json`, which is the count). A class that merely contains the name (`field-label-row`) is another class, and a component handed `labelClassName="nv-field-label"` draws no such element itself. `help` is a muted line under the control (`field-help`) that describes it: the control's `aria-describedby` lists it before the error, and a row with no native control is a group described by it. **The console overlays** (`ui/components/console/nv-overlays.jsx`: New session, New agent and the rest) draw their fields with `NV_Field`, which was a `<div className="nv-field-label">` over the control, so none of them named its control and the count above never saw them; it is now `FormField` with the overlays' class names (`.nv-field-label` is `display: block` so the `<label>` lays out as the div did), the Name and Initial instructions fields are found by their label (a `hint` is a word of its own in the name, "Name optional": the row puts a space before it, and `.hint` / `.nv-field-hint` have a 3px margin for that space's width), and the fields around a custom widget (the agent/graph picker, the autonomy switch) are groups named by it. The graph-input rows of the New session overlay are `SharedNewSessionSchemaField` (`new-session-form.jsx`), now a `FormField` whose `help` is the schema's description (baseline 7 to 6). **The agent form** (`agents.jsx`, `AG_NewAgentModal`) had already given its plain inputs an `id` and a `htmlFor`; its three custom-widget rows are now `FormField` groups named by their label (the model-profile picker, the system-prompt parts, the tool picker), every system-prompt part is a textarea with its own `aria-label` ("System prompt part 1"), and the locked summary of a harness-managed agent is a `<dl>` (`AG_ManagedSummary`) instead of four `<span className="field-label">` captions (baseline agents 7 to 0; a managed agent cannot be created through the API, so that summary is covered in V8, not in a journey). The large create form that shared that file (`SharedNewSessionForm`) had no consumer (the script was loaded, `window.SharedNewSessionForm` was read by nothing, only comments named it) and is removed with its 6 bare labels and its static tests (`tests/ui/test_retired_new_session_form.py` keeps it gone); `new-session-form.jsx` holds only the graph-input row, which the overlay renders. NOT done: the other conversions; the mobile New session sheet (`nv-mobile-shell.jsx`) has a name input and an instructions textarea with a placeholder and no label; the count does not see a label with no `field-label` class, a class set by an expression, or a comment trailing code on the same line. (`tests/ui/test_form_rows_label_their_control.py` runs `FormField`, the three wrappers and the graph-input row in V8, `tests/ui_e2e/test_new_session_overlay_labels_journey.py` the real overlay; `tests/ui/test_field_label_ratchet.py` checks the scanner on synthetic JSX before it checks the tree.)

**The console has landmarks, a page heading and live regions.** On desktop the activity bar is `role="navigation"` named "Views", the topbar `role="banner"`, the rail `role="navigation"` named "Sessions and workspaces", the Files panel `role="complementary"` named "Files", and the shown view (`.nv-view`) is the one `role="main"`, headed by a visually hidden `h1.nv-sr-only` ("Studio", "Platform" or "System settings"; the overlays and pages keep their own `h1.page-title`). On a phone `.nv-mobile-shell` is the `main` landmark. The toast host draws two sibling live regions inside a stack that is not one itself (`nv-toasts-status`, polite `role="status"`, and `nv-toasts-alert`, assertive `role="alert"` for error toasts; an alert nested in a status region is announced twice by some screen readers). Because they are two regions, toasts of the two kinds are not interleaved in arrival order: within each region they are in arrival order, and the polite region is drawn above the assertive one. In the session document only the WORDS of the running status strip are a live region (`nv-status-live`, `role="status"`; `SH_statusWords`), the elapsed time beside it (`nv-status-clock`) is not, because a status region is atomic and the clock ticks every second; the reconnect note is `role="status"`. A pending approval card (`NV_DecisionCard`, prop `live`) and a failed turn's error card are `role="alert"` only when they ARRIVE while the document is open: `NV_useFirstLoadKeys` freezes the keys the first load of the history and of the pending gates brought (those are history and stay quiet, so opening a session with three past failures fires no announcement), and a card on a session that is over is never an alert (`ended`). The composer's accessible name is its current hint (`composerHint`: "Message <agent>...", "Steer mid-run ...", "Send to reopen this session..."), the same string as its placeholder, which changes with state and is not a name on its own, and the Platform list filters are named "Filter <page>". The streamed reply itself is not announced token by token; the status strip and the settled records are.

**An approval card's reject form says when it sends and can be folded (console review C-018).** `NV_DecisionCard` (`ui/components/console/nv-session-doc.jsx`) keeps one button for both steps: "Reject with feedback" at rest, whose first click only opens the reason box (focused, `aria-label="Reason for rejecting"`). Once open the same button reads "Send rejection" (red outline through `data-armed`, disabled until the reason has text) and `Cancel` (`nv-reject-cancel`) folds the form without a request and drops the draft, so the next open starts empty and its first click cannot send old text. Approve is never affected by an open form, and an ended session keeps the card read-only. (`tests/ui/test_decision_card_reject_form.py` runs the card in V8; the CI journey `tests/ui_e2e/test_approvals_journey.py` drives the same open, cancel, reopen cycle.)

**A trace row says what its badge means and what a model call cost (console review C-017).** Both trace surfaces, the session document's sidebar one-liner (`NV_TraceLine`) and the maximize overlay's expandable row (`NV_TraceRow`), draw their badge through one component, `NV_TraceGlyph`: `T` is named "Tool call" and `A` "Model call" (a `title` for the pointer and an `aria-label` on a `role="img"` span for assistive tech; the letters alone had no legend). A model call's row also says its tokens before its duration, from the timeline node's own `input_tokens` and `output_tokens` (`NV_traceTokens`: "1.2k in · 56 out", exact below a thousand, then `k` and `M`; only the count a call reported is shown, nothing for a tool call or a call that reported none). Not done: a legend in the pane itself and a token total in the pane header. (`tests/ui/test_trace_row_labels.py`, `tests/ui_e2e/test_trace_labels_journey.py`.)

**The session state chip says Ready for a session that merely rests.** The served `session_state` is coarse on purpose: `parked` covers every WAITING or PAUSED row that has completed a turn (`WorkspaceSession.session_state`), so labelling it by that word alone told the operator that every session that had simply answered was blocked. The header chip (`NV_SessionStateChip` in `nv-session-doc.jsx`) keeps `data-state` as served (the e2e journeys and tools read it) and decides the label from what the row stores, in `NV_sessionStateChipView`: a `parked_status` is a real park (an approval, an answer or a timer) and reads amber `Parked`, `status: paused` is the operator's pause and reads `Paused`, and any other row that rests reads `Ready` with `data-resting="true"`, drawn neutral. The richer per-reason wording ("Waiting on approval") is `describeSessionState` in `session-state.jsx`.

**A worker that has not reported its load is unknown, not idle.** `GET /v1/workers` rows and `/v1/health` serve `in_flight: null` for a worker from before load reporting, or one that has not yet sent a heartbeat with a load (#484). The Workers page (`workers.jsx`) keeps the null: a row reads "? / 3" and its bar is drawn dashed and empty with the title "Load not reported", the detail panel says "load not reported", the drain dialog says "its in-flight sessions" instead of a count (`WK_inFlightText`), and the "Running now" tile (`WK_fleetLoad`) sums only what was reported and reads "? / <slots>" with "1 worker not reporting its load" or "N workers not reporting their load" (`WK_unreportedText`) while any worker that can run something has not reported (dead workers are tombstones and count for nothing either way). The legacy health page charts nothing and prints "n/a" for an unreported total. The system dashboard already printed "n/a". Before this the page turned the missing number into 0, so an overloaded fleet of old workers read as idle. Since 2026-10-18 (D4) the console no longer mounts the Workers page: the Dashboard's worker card is the one worker surface, and `workers.jsx` stays for the docs embed `workers-stats`.

**The Dashboard's Setup card (2026-10-18, D6).** `NV_SysSetupCard` (`nv-system.jsx`) renders the six live checks from `GET /v1/setup/state`, read once and never polled (each read lists the LLM provider's models). Failing checks are listed with their fixes: "Open Providers" navigating to Platform > Providers, or "Re-run seed". The actions menu offers Check again, Re-run seed, and Reset default agents behind a danger confirm dialog. Seed errors are told as error toasts, details are sanitized through `SW_tidy` to keep credentials out of view, and the Installed extras table is available as a folded list. Pinned by `tests/ui/test_system_setup_card.py` and the journey `tests/ui_e2e/test_system_setup_card_journey.py`.

**The System dashboard's health cards say what the server says (console review C-036).** `NV_HealthCards` (`nv-system.jsx`, also the phone's More tab) reads `GET /v1/health`, `GET /v1/sessions?session_state=running&limit=1` and, for the attention card, the aggregate `GET /v1/yields/pending`. The "sessions active" card used to ask for `status=running`, which also counts a session parked on a yielding tool and one queued for a worker that has not claimed it, so "running now" was wrong for both; `session_state=running` is the turn in flight right now, the same derived state every session row serves. The scheduler card shows `scheduler.detail` under its word when the scheduler is alive and not degraded ("in-memory scheduler (single process assumed)" on the default install, where the process cannot tell that it is the only one), "healthy" when the server sends none, `degraded_reason` when it is degraded and "no scheduler attached" when it is not alive; while `/health` has not answered it reads "checking…" in the neutral dot colour, not the red of "no scheduler". `tests/ui/test_health_cards.py` runs the component in V8 with the resource hook answered from a table (the path asked, the total, each reading) and `tests/ui_e2e/test_system_dashboard_cards_journey.py` compares the real cards with the real endpoints.

**Stop is acknowledged.** `POST .../interrupt` returns before the turn has stopped, so the session document shows a "stopping" state until it has: `SH_isStopping(session)` (`ui/foundation/shell-status.js`) is true while the served `interrupt_requested` flag is set on a live session (the worker clears it when the Stop lands), and it is OR-ed with `stopPending`, the click's own state, so the button disables the instant it is pressed. While stopping, the composer's Stop and the status strip's interrupt button are disabled ("Stopping..."), and the strip says `stopping` (or `stopping: ending <tool>`: a Stop cancels a running tool, except one that must not be cancelled, such as a file write, which it waits for a few seconds, and the strip cannot tell which; `SH_stoppingLine`). Every entry point (the buttons, the `session.interrupt` palette verb, the rail's session menu) goes through `NV_doInterrupt`, which shares the pending request when pressed twice and toasts what actually happened: "Stopping the turn" only when the returned row carries `interrupt_requested: true`; "Nothing to stop: no turn is running" when the server answered 200 as a no-op (it does so on every row that is neither running nor parked: idle, waiting, paused, a turn that just finished), which also clears the click's pending state at once; and an ERROR toast with the request id on a failure. Every entry point is also gated on `SH_canStop(session)` (the server's own condition: a RUNNING row that is not parked): the composer's Stop and the strip's interrupt button render only for such a turn (or while one is stopping), the rail's session menu offers Interrupt only for it, and the `session.interrupt` verb is registered with an `available(ctx)` predicate that the palette's ranker applies to the focused session's row (`NV_focusedSessionRow`; the verb registry keeps `available` on its explicit whitelist, as it does `requiresLive`, which nothing evaluates yet). A Stop's `cancelled` record reads "stopped" in the transcript and a Cancel's reads "cancelled" (`SH_lifecycleLabel`). A pending click clears itself after 5 seconds if the served flag never appears, and the client's pending leg obeys the same parked/ended exclusions as the served flag (`stopPending && SH_canStop(session)`), so a parked row never reads "stopping". A PARKED session is never "stopping": no turn is running while it waits and the server refuses a Stop on it with 409, so the rail's session menu does not offer Interrupt for it, and a Stop that is refused anyway (from the palette verb, or a race) shows the server's reason in the failure toast and clears the click's pending state.

**A clean turn end says nothing; an unclean one says why (console review C-016).** The slim row that closes a turn (`NV_LifecycleRow`, `nv-turn:<seq>`) is the turn boundary and carries the turn's trace button (`nv-trace-open:<seq>`). `SH_lifecycleLabel` returns no label for a `done` that ended cleanly (`stop`, `stop_sequence`, `other`, or no reason), so the row draws the button alone instead of printing the record's name ("· done") after every answer. A `done` that did not end cleanly is named: `max_tokens` "cut off at the output limit", `content_filter` "blocked by the content filter", `error` "ended with an error", `tool_turn_cap` "stopped at the tool-turn cap". `yielded` and `resumed` still read "· yielded" and "· resumed", and a cancelled turn reads "stopped" or "cancelled". The trace button stays on the row because there is no other per-turn place for it yet; moving it onto the answer block would let a clean end draw no row at all. (`tests/ui/test_done_marker_row.py`; `tests/ui_e2e/test_trace_sidebar_journey.py` checks a real turn.)

**An idle session document polls slowly; anything in flight polls fast.** One open session that was doing nothing made about 110 requests a minute (the session row every 2 s, the pending yields and the external-tool banner every 5 s, the session list and the Files tree every 5 s, the workspace list twice every 15 s). `NV_sessionIsCalm` (`nv-session-doc.jsx`) says when the live tap and the refetch on its frames carry every change, so the polls only catch up: the tap is connected, no live status is showing, no send or Stop is waiting for the row, and the row says `turn_status: idle` with no interrupt, pause or cancel requested. The session row, the pending yields and the banner (`pollMs` prop of `ExternalPendingBanner`) then poll every `NV_CALM_POLL_MS` (15 s) instead of 2 to 5 s. The state is reached only after the session has been at rest for `NV_CALM_AFTER_MS` (5 s), because a turn's last frame can arrive before the row shows where the session came to rest, and it is dropped the moment anything stirs; a tap frame (`yielded`, `resumed`, `done`) also refetches the row, so a slow poll never delays one. While a session is calm, a change to its row that sends no tap frame (a rename, or the session ended from another client) takes up to 15 s to show; a frame, a Stop or a send brings the fast cadence back at once. The Files tree polls every 15 s instead of 5 s while no session of its workspace is running (`NV_anySessionRunning` over the shared session list), and the rail, the shell and the Files sidebar read that list through one hook, `NV_useSessionList`, so they cannot disagree about its cadence. The session list itself stays at 5 s on purpose: a session created elsewhere emits no tap frame, so the poll is how it appears in the rail. The shell and the rail used to fetch `GET /v1/workspaces` under two cache keys; it is one (`nv-workspaces`). A hidden tab already stops polling (`use-resource.js`), and the global idle mode still skips every poll that has not opted out. A measured idle session document (30 s, steady state, `tests/ui_e2e/test_idle_session_polling_journey.py`) makes about 27 requests where it made about 55.

**The running strip is the tap's word, checked against the row.** The strip's live status (`thinking`, a tool name) is held by the session store (`ui/foundation/session-store.js`) and comes only from tap frames: a user message or a tool call sets it, a terminal record (`done`, `cancelled`, `error`) clears it. **A workspace that cannot be read is said so, not drawn as an empty conversation.** The session document's history read (`GET /v1/sessions/{id}/messages`) answers a typed 503 `/errors/workspace-unreachable` when the session's workspace exists but its runtime does not answer (it used to answer an empty list, which looked like the history was gone). `NV_historyProblem(history.error)` turns that one type into a banner above the transcript (`nv-history-problem`, `role="alert"`: the workspace is unreachable, the conversation is not lost, check the workspace's status, with a "Try again" button that re-reads); the resource keeps polling, so the banner clears on its own once the workspace answers. **A failed session says why, and a failed turn is one card.** The end divider (`session ended . <reason>`) gets a note under it from `NV_endedLine` (`nv-session-doc.jsx`): for a failed session the reason in user language and the next step (`ended_detail` `never_started` reads "It never started: the workspace or the agent could not be prepared."; a code the table does not know is shown rather than hidden; the snake_case codes a failed model call carries, `server_error`, `network_error`, `rate_limit`, `auth_error`, `stream_timeout`, `generation_timeout`, `context_overflow_unrecoverable`, `bad_request` and `connect_timeout`, read from one table, `NV_failureWords`, as a plain clause plus a next step specific to that failure), the same for workspace lost and the tool-turn cap, and nothing for the quiet endings (completed, cancelled, deleted). A failed stream writes its error with the cause and then a bare terminal marker (`{reason, terminal}`); `SA_toTranscript` (`session-adapter.jsx`) folds that marker into the cause written earlier in the same turn (a turn is what lies between two user messages), while a marker with no cause in its turn stays so the failure is never invisible. A model that dies mid-answer writes the stream's own Error row and then dispatch's ERROR record with the same message; the later copy from the same node is folded into the first, which carries the specific code. The same rule can fold a crash or reclaim marker into the retried attempt's failure when both carry the same words in one turn; that is accepted, since they say the same thing. The fold leans on the writers' order (the cause is written before its copies and its marker): a copy written before its cause would be the row kept, a marker that came first is removed when the cause arrives, and a row without a node id matches a cause of any node, so two graph nodes failing with the same words stay two cards only when both rows name their node. Parent and subagent failures never fold into each other (`SA_failureScope`: a delegated record carries `delegated` and `delegate_run_id`, or `delegate_tool_call_id` before runs had ids), because a subagent's row is drawn inside its own block and a parent turn that hit the same provider error would otherwise have no card of its own at the top level; a bare marker belongs to the scope that wrote it. The scope is the run id when the record has one, else the delegating call id, else a single shared `delegated` scope: two runs of one tool call stay two scopes, records written before either id existed all share the one, and a grandchild's failure (a subagent's own subagent) carries its own run id and draws in its own block. A non-fatal error (an explicit `fatal: false`: the provider reported a problem and the stream went on) is not a failure and is not folded: `SA_toTranscript` makes it a `retry_notice` row, never the cause a later failure folds into, and it is usually the first half of a failure: the agent loop holds a stream's first Error as the call's end and raises when the stream finishes, so dispatch writes its own ERROR with the SAME words (then the release marker), and a failure of the same scope (and node, as for copies) with the same words ABSORBS the notice, in either order and whatever output lies between them, leaving one red card (the failure keeps the notice's specific code when it has only the generic `/errors/internal`, since the code chooses the card's words) (the failure row, which is the one the server counts as the turn's end). A failure with other words, or in another turn or scope, leaves the notice. `NV_noticeView` draws it as a quiet line (`.nv-turn-note`, no alert role, no trace button) in one of three states settled by `SA_settleNotices` from the rows after it in the same turn and scope: `retrying` (amber: nothing followed yet), `recovered` (grey: output, or a done, followed) and `ended` (a failure card, a cancel or the next user message followed with no output). Output wins over a later ending, whatever came between. With the producer that exists today (the OpenResponses `error` event) `recovered` cannot happen: the loop fails the turn on ANY held Error, so the notice is always absorbed by dispatch's failure; the state is kept for an Error yielded after Done and for a loop that goes on (design ticket 01a11c07). A notice stays amber while live parts stream after it, because the live parts are not rows of the transcript yet and `retrying` is settled from the rows. A subagent's notice and a subagent's failure sit in its subagent's block, and `NV_subagentRows` draws both there (they carry no `label`, their words are in `payload.message`, so the label rule alone used to drop them and a subagent that failed showed nothing): the failure as the same red card with the same words (`NV_errorView`), the notice as the same quiet line (`NV_noticeView`), each under the subagent's name, neither announced as an alert (it arrives inside a block the reader may not be looking at; no `role`, no `aria-live`) and neither with a trace button (a trace belongs to the session's turn). The name is the delegating `system__invoke_agent` call's `arguments.agent_id`, because `DelegationRecorder` stamps no `agent_id` on the records it writes (a record that does carry one keeps it). The only producer of a non-fatal Error (the OpenResponses stream) makes the agent loop hold the Error, yield the Done first and the Error last, and raise, so the delegating call is answered with an ERROR result and the delegated scope gets NO failure record of its own for the notice to be absorbed by: a delegated notice whose delegating call FAILED and whose words the call's error output QUOTES is therefore drawn as the failure, the block's one red card, in the notice's words (`SH_callQuotesNotice`: a failed `invoke_agent` answers `{type, message}` with `subagent 'x' LLM stream failed: <the stream error's message>` and the resume path `{error}` with `subagent LLM stream failed: <the stream error's message>`, so the words END the text (read from `message`, else `error`, else the text itself; at a word boundary); the same words in the middle of an unrelated failure promote nothing; when a scope has several notices it is the LAST one the output quotes, so a call never shows two red cards, and a call that failed for a reason no notice names promotes none); a notice whose call has any other result never says the turn is continuing (the call is over, so a `retrying` notice reads as carried on); while the call is still running it is the quiet line in its own state. A call is paired with its result by RUN and scoped call id (`SH_nestWithResults`, `SH_resultForCall`: the key is the record's `delegate_run_id`, else `call:<delegating call id>`, else empty for the parent turn's own records, then `|` and the call id), with the index taken over the WHOLE transcript before nesting: the recorder writes a delegated run's tool results like any other row (`run_agent_turn` yields the call's `_ExecutorToolResult`, `run_subagent` feeds it to the recorder) and numbers scoped ids per run, so a child's call and its parent's are both `x:tool:1:1`; indexed by the id alone, and only at the top level, a nested call block showed its PARENT's result and a grandchild's notice read the parent's OK result ("carried on") or, with no collision, found none ("continuing") under a finished parent. Three rules follow for a page. Its effects run before its new body is in the DOM whenever it re-renders on its own (the slots draw the body in a nested update that follows the page's commit), so a page effect that reads or focuses body DOM must wait a task or live inside the body, as a small component in it whose effect runs once the body has been drawn; the form's focus hand-off after a Try again (`PC_FocusAfterRetry`) is one, and the page effect it replaced saw the old Try again button still focused, did nothing, and let the focus fall to `<body>` (`tests/ui_e2e/test_register_overlay_focus_journey.py` pins it in a browser). React context that a page provides does not reach its body, because the body is drawn in the shell beside the page and not under it: hand the body what it needs in props. And a page must keep returning `frame(...)`: it is the page's only way into the dialog, anything else a page returns is drawn beside the dialog and not in it, and when a page stops calling `frame` its publisher takes back what it published, so the dialog shows no body and no footer for it and no stale handler can be pressed. `busy` says that a request of the page's own (a save, a test) is out: the overlay then keeps the type selector shut and holds Delete off until it is answered (a switch would unmount the page and swallow the answer), and a request starting clears a refused Delete's message from the error line. ## 5. Data model

The console's own data model is its URL grammar, which is the only thing it persists between loads:

```
#/w/{wid}?doc=<kind>:<ref>&overlay=<name>[:<section>[:<id>]]#<anchor>
```

The grammar also carries the view (`view=platform:<nav>[:<sub>]` / `view=system:<nav>`; absent means studio, so every historical URL parses forward). A nav that has sub-entries takes a third segment, the `<sub>`: today only Platform > Providers does, and its sub is the provider type, one of `llm`, `embedding`, `ssp`, `cross_encoder`, `workspace`, `web_search`, `channel`, `artifact_storage`, `tts`, `stt` (`view=platform:providers:tts`; the sidebar's order, TTS and ASR last; every one is a key of `PROVIDER_CLASSES`). The lists live in `SH_VIEW_SUBS` (`ui/foundation/shell-url.js`), keyed `<name>:<nav>`, and the manifest mirrors them as `view_subs`. A sub the list does not name is dropped on parse and never written, so a link to `view=platform:providers:bogus` opens Providers (every type) and the address bar is rewritten to `view=platform:providers`. The Platform navs are `providers`, `profiles`, `agents`, `graphs`, `templates`, `toolsets`, `tools`, `collections`, `web`, `triggers`, `channels`, `harnesses`, `services`, `approvals` (the sidebar's order) and the System navs `dashboard`, `users`, `apikeys`, `sso`, `mcp`, `internal`, `activity`, `profile`; `web` and `templates` are custom pages (section 4). Two retired navs are answered by a redirect that `SH_parseView` applies before it validates the nav (`SH_VIEW_REDIRECTS`, on `window`): `view=platform:workspaces` opens the studio and `view=system:setup` opens the System dashboard, and the address bar is rewritten to the target (`view=platform:templates` needs none: it is the new page). `overlay=workspaces:<id>` (a workspace's settings) and `overlay=providers:<class>[:<id>]` keep parsing. Four doc kinds are addressable: `session`, `file`, `diff`, `wiki`. The overlay names are: `providers`, `collections`, `agents`, `graphs`, `triggers`, `toolsets`, `approvals`, `harnesses`, `services`, `channels`, `workspaces`, `new-session`, `new-workspace`, `internal-collections`, `activity` (the old `admin` overlay's sections are the System view's navs). An anchor is either `turn-<n>` or an `L<from>[-L<to>]` line range. Both lists are pinned against `ui/fixtures/shell/manifest.json` by a test, so the vocabulary cannot drift from what the designer package documents.

Beyond that, pages own no durable server data of their own. The entity schemas they render (Agent, Graph, Collection, Toolset, the provider models, WorkspaceSession, Trigger, ApiToken, and so on) are owned by their backend subsystem docs. The only page-held state is ephemeral React state: the active filter/sort/page, the selected row, the open-modal draft and its `fieldErrors` map, and per-page UI-only data such as the graph editor's `x/y` node coordinates (stripped before `PUT`). Cache keys are page-scoped strings on the foundation `useResource` map, listed per page above; they are an index into the shared cache, not a data model.

**Landing.** With a workspace resolved, the shell opens the most recent session as a pinned tab. An empty workspace creates one lazily, bound to the system default agent, so the console is never an empty frame asking what to do.

The dominant lifecycle inside an overlay is the CRUD-page round trip: the list bar mounts and its `useResource` poll loads the page of rows; the operator filters and clicks a row, which `navigate`s to the detail route; the detail page mounts, polls its own key, and renders the active `?tab=`; the operator opens the create/edit modal or a delete confirmation; on submit the `useMutation` fires the `POST`/`PUT`/`DELETE`, invalidates the relevant cache keys, and both surfaces refetch. A detail's Delete (after its toast) and Back call `navigate("/<plural>")`, which the shim reads as "close the overlay and select the entity's Platform page" (see [ui-foundation.md](ui-foundation.md)), so the list is never drawn inside the overlay. Success pushes a toast; a 422 maps to inline field errors in the modal; a 409 cascade conflict renders inline inside the delete confirmation as a `Banner` so the operator can resolve the dependency.

```mermaid
    Op->>L: filter (poll pauses on input focus)
    Op->>R: click row -> navigate(/x/:id)
    R->>D: mount SessionDetail/AgentDetail/...
    D->>API: useResource GET /v1/x/{id} (+ tab sub-resource)
    API-->>D: row -> header + active ?tab=
    Op->>M: Edit (modal reused with existing) / New X
    M->>API: POST or PUT-replace
    alt 200/201
        API-->>M: ok -> invalidate keys, refetch L+D, toast
    else 422
        API-->>M: ProblemDetails -> inline fieldErrors
    else 409 (delete cascade)
        API-->>D: conflict -> inline Banner in confirm modal
    end
```

Loader, empty, error, and confirmation conventions across pages: on first load a list shows a skeleton table (or simply renders zeros on metric boards); `loading=true` fires only on the first fetch for a key so background polls never flicker (a foundation guarantee). An empty result renders an entity-specific empty-state row or card with a "New X" call to action rather than a blank table. A fetch error retains the last good data (stale-while-error) and surfaces the error title; after three consecutive failures the poll halts until a manual Refresh. Destructive actions always go through a confirmation `Modal` whose body spells out consequences (in-flight counts, idempotency notes, the "second DELETE returns 404" caveat, the list of dependent rows for cascades) before the mutation fires.

A few pages run non-CRUD lifecycles. The session detail page reads the authoritative top-level `GET /v1/sessions/{id}` (never the nested workspace path, which is known to drift) and routes signals through the workspace-scoped POSTs; its five tabs are Overview, Messages, State, Files, and Turn log, and it additionally mounts a live stream panel fed by the workspace tap (an SSE `EventSource` on `GET /v1/workspaces/{wid}/tap`) plus the yielding-tool panels (AskUser, WatchFiles, Sleep, ApprovalBanner) and the `TurnLogTab` whose endpoint resolver picks the session route for agent bindings and the graph-run route for graph bindings. The internal-collections page derives one of three states (Inactive / Configured / Active) from a single config probe and drives a phase-aware bootstrap progress panel with adaptive 1s/5s polling. The graph detail page seeds an editable draft, auto-lays-out node coordinates, runs a client-side topology validator that gates Save, and issues a destructive `PUT`-replace.

## 7. Persistence

Pages persist nothing of their own to the server beyond the CRUD mutations enumerated above, and nothing to client storage. The small set of client-persisted preferences (theme, sidebar collapse state, the force-desktop opt-out) is owned by the foundation tweaks store and documented in [ui-foundation.md](ui-foundation.md). One historical client-persistence heuristic was deliberately removed: the internal-collections page once contemplated a `localStorage` "bootstrapped" flag, but the shipped page derives its state from the server-side `activated_at` field on the config row instead, so every client and operator sees the same truth. The `useResource` cache is in-memory and rebuilt from the API on every load.

**Platform verbs and the custom-page verb rule (Platform revamp 01, Task 9).** Every Platform page and every provider type is a palette verb on the `platform-nav` surface, with the ids `platform.open.<nav>` and `platform.open.providers.<type>` and labels such as "Open Providers", "Open Providers: Semantic Search Storage", "Open LLM Profiles" and "Open Approval Policies". `NV_platVerbSpecs()` (`nv-platform.jsx`, exported on `window`) lists them in the sidebar's order, Providers then its types then every other nav, from the data the sidebar draws (`NV_PLAT_GROUPS`, `NV_platNavLabel`, `NV_platProviderTypes`, `NV_PROVIDER_TYPE_LABELS`); a page title or a type label is capitalised word by word, because the registry's label lint throws on anything but verb-noun Title Case and a throw inside the shell's registration effect takes the console down; a label the lint still refuses (a title word that starts with a digit or a symbol) is skipped by the loop with a console warning, so one odd title costs its own verb and nothing else. ## 9. Internal contracts

- **Detail pages carry their active tab in `?tab=`, read back through the router.** This makes tab state linkable and survives reload. Session detail uses `overview/messages/state/turnlog`-style ids; agents use `config/tools/sessions/metadata`; toolsets use `config/tools/sessions`; semantic-search uses `overview/config/collections`; workspaces use `files/sessions/log/channels/config/destroy` (no `destroy` for the default workspace, see the historical decision on it).

- **The create modal is the edit modal.** A non-null `existing` prop switches the submit from `POST` to `PUT`-replace, locks the id and type discriminator, and blanks masked-secret fields so the redaction is never round-tripped. Any page that edits an entity follows this, which is why there is no separate edit form to keep in sync.

- **Cache keys are page-scoped and mutations invalidate by key.** List and detail of the same entity use distinct keys (`sessions:list` versus `session-detail:{sid}`) so their independent poll cadences do not stall each other and a mutation can target exactly one surface. Shared keys are used deliberately where two surfaces must stay in lockstep (the tool-approval pending key, the IC config key shared by the sidebar bell, the knowledge OFF banner, and the dashboard tile).

- **422 maps to inline field errors; the loc-to-field mapping must match the backend emission.** Modals read `extensions.errors[].loc`, join it, and key inline errors by that path. Some backends flatten a segment out of the loc tuple (channel-provider config emits `body.{field}` not `body.config.{field}` because the model validator pre-instantiates the inner config), so the matching modal looks up the flattened key. Tool-approval validation forces a `body.*` loc prefix specifically so the approvals modal lights up.

- **409 cascade conflicts render inline in the delete confirmation, never as a bare toast.** Toolset delete blocked by an approval policy, SSP or provider delete referenced by a collection, workspace or template delete referenced by a child, and channel-provider delete all surface the conflict detail in a `Banner` inside the confirm modal so the operator can act on it.

- **Managed rows hide mutation.** Any entity carrying a `harness_id` (agents, toolsets, collections, documents, graphs) renders a "managed by harness" banner and hides the Edit button, mirroring the backend's 409-on-public-CRUD discipline.

- **The Platform page entry.** Each id of `NV_PLAT_PAGES` (`ui/components/console/nv-platform.jsx`) is one generic Platform page: `title`, `noun` (singular and plural), `list(apiFetch, signal)`, `card(row, con)`, `open(con, row, setModal)`, `create(con, setModal)` with its `createLabel` (the header action's full text, the "+" included: "+ Agent"; `null` for a page with no create), `delPath(row)` (null when the card's "⋯" menu has no Delete, as for a built-in toolset), an optional `extraNav` (a secondary header button) and, for a page whose list is slow to build, `poll: false` (no 15 s re-poll) with `refresh: true` (a Refresh button in the header).
  - `card(row, con)` answers the one card view model of every Platform page (seam I-8): `{ id, name, sub, label?, badge?, icon?: { path, tone? }, status?: { label, tone, onClick?, testid?, title? }, facts }`; `label`, when set, names the card's controls where `name` alone is ambiguous (the Tools entry sets the scoped id, so two toolsets' `search` tools are "Open acme__search" and "Open docs__search", audit G1-21). An entry maps its own row fields freely; only the returned shape is fixed (`tests/ui/test_platform_card_view_model.py` holds every entry to it).
  - `id` is the record id (a tool's scoped id, since two toolsets may each have a `search`). `badge` is a short neutral word: "built in", a tool's toolset, a backend kind, "system". `status` is the row's state, with a tone of `ok`, `warn`, `error` or `muted`. `facts` are strings (one line) or `[key, value]` pairs, `null` for a missing one (`NV_fact`); every renderer drops the nulls and draws at most three.
  - `con` is the console (`NV_useConsole()`), so a status with `onClick` can open a dialog or an overlay. Such a status is drawn as a button named by its label (test id `status.testid`) above the card's stretched Open, and a click on it never opens the card. On the phone it is a touch-target button on the fact sheet that closes the sheet, then runs.
  - An entry may set `emptyText` and `emptyAction: { label, run(con) }` (seam I-9). With no rows, the empty state shows `emptyText` instead of the generic `NV_emptyText` sentence, and a button that runs `emptyAction.run(con)` (`nv-plat-empty-action`; on the phone a tap-sized `nv-mob-plat-empty-action`). Without `emptyAction` the page keeps its create button when it has one. A filter that hides every row still says "No X match" and offers Clear filter (`tests/ui/test_platform_empty_states.py`).
  - The LLM profiles page uses both hooks. It has no single-profile create: a single profile comes from the Register provider overlay's import. Its one action is `+ Aggregate` (`createLabel`; its `create()` hosts the profile overlay with no row, and `MP_ProfileModal` draws that as the aggregated profile's create form, `tests/ui/test_llm_profile_overlays.py`). Its empty state reads "No LLM profiles yet. Register an LLM provider to import its models." and offers "Open Providers › LLM" (`con.goView("platform", "providers", "llm")`). Its cards are `MP_profileCard`'s (`model-profiles.jsx`): a single profile is badged "imported" with "provider · model" under its name, an aggregated one "aggregated" with "N profiles · sequential fallback" (or "· round robin"); the facts are the context window, the usage ("bound by 2 agents · 1 graph node", or "unbound") and "managed by <harness>" when a harness owns the row, every one a `[label, value]` pair of strings for the phone's fact sheet. Its `list` passes the answer through `MP_withWindows`, which gives each aggregate `_window`, the smallest window of its members in the same answer (the minimum `primer/model_profile/resolver.py` takes at resolve time, served on no route), so the card reads "262,144 tokens (smallest)" or "unknown" when a member is not in the answer, never a guess. `delPath` answers null for a harness-managed row (the server answers 409), so its card has no Delete (`tests/ui/test_llm_profiles_page.py`).
- **`con.goView(name, nav, sub)` is the one way to change the view.** `sub` is optional and is the provider type when the nav is `providers` (`con.goView("platform", "providers", "web_search")` writes `?view=platform:providers:web_search`); it means nothing for a nav that has no types, and the URL builder drops it there. A page that sends the operator to a provider type names the type: the empty channel create ("Add a channel provider") goes to `channel`, the empty LLM profiles page to `llm`.
- **Session detail pins the authoritative read path.** It always reads top-level `GET /v1/sessions/{id}` (and polls it), never the nested `/v1/workspaces/{wid}/sessions/{sid}` path, which is known to drift after signals; signals themselves still go through the workspace-scoped POSTs.

## 11. Historical decisions

- **Session detail pins the top-level `GET /v1/sessions/{id}` read for both initial fetch and polling, never the nested workspace path.** Why: the nested path drifts after pause/resume/cancel/steer (pinned by T0399/T0555/T0611) and the top-level row is the only authoritative view. Spec: docs/superpowers/specs/2026-05-16-ui-sessions-design.md.

- **List and detail of the same entity use separate `useResource` cache keys with separate poll cadences.** Why: detail is the action surface and polls faster (2s) while the list is a directory view that polls slower (3s to 5s); separate keys keep one from stalling the other and let mutations invalidate either independently. Spec: docs/superpowers/specs/2026-05-16-ui-sessions-design.md.

- **The create modal doubles as the edit modal across every CRUD page, with id/type locked and a `POST`-versus-`PUT`-replace switch.** Why: it avoids duplicating the form schema and the 422 field-error mapping between create and edit, and `PUT`-replace matches the storage-level full-replace contract. Spec: docs/superpowers/specs/2026-05-16-ui-providers-design.md.

- **Edit mode blanks any field still holding the `**********` secret redaction before submit.** Why: round-tripping the literal asterisks would clobber the stored secret; blanking lets the backend keep the existing value when the operator leaves the field untouched. Spec: docs/superpowers/specs/2026-05-25-designer-handoff-ui-spec.md.

- **The agent create form refuses a bad name and a missing description before it posts, and the agent status strip prints no developer line.** Why: `Bad Name!` was accepted as an agent id (`POST /v1/agents` answered 201, the model had no id pattern) and one press of Create on an empty form made a nameless agent whose description the form had replaced with "(no description)"; an id is permanent and sits in URLs and references, and a description is how OTHER agents find an agent (admin review 2026-10-08, ADM-14). The pure `AG_validateNewAgent(id, description)` (`agents.jsx`) returns refusals under the server's own field paths (`body.id`, `body.description`), so a client refusal and a server 422 share one display (the id field had none for a server error). The id is optional (the backend assigns `agent-<hex>`), but a typed one is lowercase letters, digits, hyphens and single underscores (two in a row are reserved for the agents a harness install mints, `<slug>__<template>`), starting with a letter or digit, at most 63 characters; surrounding spaces are dropped and a whitespace-only id is a blank one (it used to be sent as `"  "`, which the server then accepted); the description is required, on create AND on edit: clearing the description of an existing agent used to save the literal "(no description)", and what is sent is the trimmed description. An edit passes a blank id to the check (an existing agent's id is locked), so it can only be refused for its description. The backend enforces the same two rules on create (`primer/agent/agent_checks.py`, ticket 01a11c1c: a 422 at `body.id` or `body.description`, which this form's `fieldErrors` already displays; the system tools and the builder answer `validation-error`), and `tests/ui/test_agent_form_validation.py` fails when the form's regex and the backend's `AGENT_ID_PATTERN` differ or when the two disagree about an id; the client check stays so the person is told before the request goes. The status strip under "All references resolve" printed `GET /v1/agents/<id>/status · last checked just now · polled every 30s` (ADM-15: an endpoint and a poll interval, and "just now" was a fixed string); it now says "Checked automatically while this window is open" with the endpoint and interval in a tooltip. `tests/ui/test_agent_form_validation.py` runs the check in MiniRacer and pins how the form uses it; `tests/ui_e2e/test_agent_form_journey.py` drives the real form and the seeded operator's strip.
