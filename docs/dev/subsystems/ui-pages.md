# UI Pages

## 1. Purpose

This doc covers the operator console: the pure shell modules under `ui/foundation/shell-*.js`, the three-view console under `ui/components/console/nv-*.jsx` (plus the two `ui/components/shell/` survivors, `sh-api.jsx` and `sh-activity.jsx`), and the page components under `ui/components/` that it hosts. The console IS the studio. There is no page router, no sidebar and no per-page chrome: one workspace-scoped surface, whose navigation is a verb registry, whose documents are deep-linkable tabs, and whose management surfaces are overlays re-hosting the page components unchanged.

It owns the shell's own model (the URL grammar, the tab semantics, the verb registry, the dual-render rule) and the repeating page shapes those overlays still use: the list-bar plus detail-tabs structure on CRUD entities, the find-bar plus table plus create-modal triad, and the loader/error/empty/confirmation conventions every page reuses.

It deliberately does not re-document the primitives these surfaces build on. The HTTP client, the polled `useResource` cache, optimistic `useMutation`, the router shim, the toast queue, the tweaks store, the idle and viewport hooks, and the shared widgets (`Modal`, `Banner`, `Btn`, `Icon`, `StatusPill`, `CardList`, `Fab`, `BottomSheet`, `MobileTabs`) all live in [ui-foundation.md](ui-foundation.md). The load-bearing rule from the foundation (route all I/O through the hook layer, never `apiFetch` directly) is assumed throughout.

The backend REST contract these pages consume (the `/v1/*` CRUD surface, the `make_crud_router` family, RFC 7807 ProblemDetails, the reserved-id and cascade-conflict semantics) is documented in [architecture/rest-api.md](../architecture/rest-api.md). Pages are the UI half of that contract; where a page surfaces a documented anomaly (T0025, T0379, T0711, and similar) the page-level affordance is described here and the backend cause in the relevant subsystem doc.

## 2. Conceptual model

The console is three views over one URL (the 2026-08-23 designer handoff): STUDIO (the default - a rail of session bands and files, a centre of document tabs, the composer, an optional terminal panel and events sidebar), PLATFORM (grouped nav over per-entity card pages), and SYSTEM (dashboard, users, API keys, SSO, MCP, internal collections, activity, setup, profile - reached from the profile menu). Overlays open above whichever view is active, and a command palette reaches every verb. `ui/app.jsx` is one mount, `AuthGate` wrapping `NV_Shell`, and nothing else.

**The verb registry is the routing table.** Every action a user can take is registered once, with an id, a label, the contexts it applies to and the surfaces it renders on (rail, tab menu, palette, overlay button). A surface renders the verbs the registry gives it rather than hard-coding buttons, which is what makes the dual-render rule checkable: a verb declared for a surface but never rendered from the registry, or a doc kind the URL can address that no verb opens, is an orphan, and a static guard fails on it.

**A document is a tab, and a tab is addressable.** Sessions, files, diffs and wiki pages are the four doc kinds (the trace opens as a split INSIDE the session doc; attention lives in the bands and the System dashboard). Tabs follow VS Code semantics: a preview tab is replaced by the next preview and is promoted to permanent by an edit or a pin, so browsing a file tree does not accumulate tabs.

**A management surface is an overlay, not a page.** The catalogue, agents, graphs, collections, toolsets, workers and the rest re-host their existing page components with no chrome around them. Comparison never goes in an overlay: a trace opens beside its transcript as a tab in a second group, because an overlay cannot be looked at next to anything.

Components attach themselves to `window` at module scope rather than being imported, because the bundle shares one global Babel scope; this is also why several pages prefix every top-level binding (workspaces uses `WS_`, triggers `TR_`, internal-collections `IC_`, agents `AG_`, graphs `GR_`, channels its own helpers) to avoid colliding with siblings in that scope.

The page anatomies below still hold, because the overlays host those same components.

Almost every entity surface follows one of two anatomies.

A list page is a find-bar (text filter plus entity-specific dropdowns or status chips), a desktop table (with a mobile `CardList` plus `Fab` fallback under `useViewport().isMobile`), and a create modal launched from a "New X" button. Filtering, sorting, and pagination are overwhelmingly client-side over a single `GET /v1/<plural>?limit=200` page; the poll pauses while the filter input is focused so typing is not interrupted.

A detail page is a header (breadcrumb, id, action buttons such as Edit / Delete / Invalidate / Back) over a tab strip whose active tab is carried in the URL as `?tab=` and read back through the router. The create modal is reused in edit mode: the same component takes an `existing` prop, locks the id (and often the type discriminator), pre-fills the form, blanks any masked-secret field so the redaction is never written back, and submits a `PUT`-replace instead of a `POST`.

```mermaid

    subgraph ListPage["List page anatomy"]
        FB["find-bar: text filter + chips/selects"] --> TBL["table (desktop) / CardList+Fab (mobile)"]
        TBL -->|row click -> navigate(/x/:id)| DET
        FB -.->|New X button| CM["create modal"]
    end
    subgraph DetailPage["Detail page anatomy"]
        DET["header: crumb + id + Edit/Delete/Back"] --> TABS["tab strip (?tab= in URL)"]
        TABS --> T1["Overview/Config"]
        TABS --> T2["entity tabs (Tools/Sessions/Messages/State/Files/Turn log/...)"]
        DET -.->|Edit button| CM
        DET -.->|Delete button| CONF["confirm modal (+ inline 409 banner)"]
    end
    CM -.->|POST/PUT then invalidate| TBL
```

A handful of surfaces break the mould: the dashboard and health and workers pages are read-only metric boards, the graph detail page is a drag-and-drop canvas editor rather than a tab strip, the internal-collections page is a three-state activation machine, and the docs page is a markdown reader. These are noted individually in the page index.

## 3. Architecture patterns implemented

- **The URL is the state.** Four facts are addressable and nothing else is: the workspace, the open document, the open overlay, and an anchor within the document. Palette state, toasts and every other transient are deliberately not representable, so a pasted link restores exactly what the sender was looking at and nothing they were not.

- **Registry-rendered surfaces, checked by the dual-render rule.** Verbs are registered once and each surface renders what the registry hands it. Two static guards enforce the consequences: every declared surface must actually render from the registry, and every addressable doc kind and overlay must be reachable by some verb. An address no verb reaches is a surface the user cannot find; a verb no surface renders is a promise the console does not keep.

- **Overlays re-host page components with no chrome and props only.** An overlay mount passes the component its own props and nothing else. Where a re-hosted page still calls `window.primerApi.useRouter()`, the shim answers from overlay state; see [ui-foundation.md](ui-foundation.md).

- **Every page builds on the foundation hook layer, never on raw fetch.** List polls, detail polls, modal submits, and confirmation deletes all go through `useResource` and `useMutation` on `window.primerApi`; cache keys are page-scoped strings (`sessions:list`, `session-detail:{sid}`, `graph-status:{id}`, `workspace-files:{wid}:{path}`, and so on) so a mutation on one surface can invalidate exactly the keys that need refetching. See [ui-foundation.md](ui-foundation.md) for the hook contracts and cache-key conventions.

- **List-bar plus detail-tabs is the default CRUD shape.** A `GET /v1/<plural>?limit=200` list with client-side filter/sort/paginate, a row-click navigation to `/<plural>/:id`, and a tabbed detail page whose tab lives in `?tab=`. Agents, toolsets, providers, semantic-search, channels, triggers, workspaces, collections, and graphs all instantiate this shape with entity-specific tabs.

- **Find-bar plus table plus create-modal triad.** The list bar exposes a text filter plus dropdowns or status chips; the create modal doubles as the edit modal via an `existing` prop and a `POST`-versus-`PUT`-replace switch. `PUT`-replace is the wire shape because the backend `make_crud_router` is full-replace, not PATCH.

- **Reuse-create-modal-for-edit with secret blanking.** Providers, channel-providers, semantic-search, and toolsets all pre-fill the create modal on edit, lock the id and type discriminator, and blank any field still holding the `**********` redaction so the stored secret survives. This mirrors the backend `SecretStr`-on-read masking documented in [architecture/rest-api.md](../architecture/rest-api.md).

- **Optimistic-write only for reversible edits; wait-for-200 for destructive or cascading mutations.** Description / metadata / config edits use the optimistic `useMutation` path; graph `PUT`-replace, workspace destroy, provider invalidate, and any delete wait for the response before refetching. The rationale lives in [ui-foundation.md](ui-foundation.md).

- **Anomaly surfaces are rendered in place, not hidden.** Documented backend quirks get a labelled banner or helper line on the owning page: T0025 model-list-is-static helper text in the embedding/cross-encoder provider and collection modals (the LLM provider form has no model list at all now -- see below), T0379 provider/config-not-cross-validated warning, T0711 MCP-HTTP 500 banner on the toolsets and agents Tools tabs, T0245/U0014 stdio-allowlist warning in the toolset modal. The backend cause is documented in the matching subsystem doc; the affordance is documented here.

- **Inline-for-input-validation, toast-for-action-outcome.** 422 ProblemDetails responses map `extensions.errors[].loc` to per-field inline errors in modals; non-422 failures and success acknowledgements go through the toast queue. Yielding-tool inputs (AskUser) render their 422/500 inline under the input rather than as a toast.

## 4. Code layout

The shell is split by testability. Pure logic lives in `ui/foundation/shell-*.js` as plain functions with no React and no DOM, so `tests/ui` can execute it in MiniRacer:

- `shell-url.js` - the URL grammar: `SH_parseUrl` / `SH_buildUrl`, `SH_DOC_KINDS`, `SH_OVERLAYS`, anchor parsing.
- `shell-verbs.js` - the verb registry, label lint and ranking.
- `shell-docs.js` - the tab model: open, pin, preview promotion, groups.
- `shell-status.js`, `shell-turns.js` - the status line and the transcript's turn folding.
- `shell-attention.js` - pending yields and approval records to attention items, tiered by consequence.
- `shell-router-shim.js` - `useRouter` over overlay state (see [ui-foundation.md](ui-foundation.md)).

The React surfaces live in `ui/components/console/nv-*.jsx` (the three-view flag day deleted the `sh-*` shell): `nv-shell.jsx` (the root: URL sync, the verb registry and chord dispatcher, the toast and confirm hosts), `nv-chrome.jsx` (activity bar + topbar: workspace menu with settings, search field, panel toggles, profile menu), `nv-palette.jsx`, `nv-studio.jsx` (the studio frame and the pure band sort), `nv-sessions-sidebar.jsx` and `nv-files-sidebar.jsx`, `nv-doc-host.jsx`, `nv-session-doc.jsx` (transcript, binding chip, decision/ask cards, inline artifacts, trace split, composer, voice), `nv-file-docs.jsx`, `nv-terminal.jsx`, `nv-events-sidebar.jsx`, `nv-client-tools.jsx`, `nv-overlays.jsx` (the designer create panels plus the management-surface mount table), `nv-platform.jsx` and `nv-system.jsx`. Two shell-directory files survive: `sh-activity.jsx` (the events console the System view re-hosts) and **`sh-api.jsx`, the only file that names a URL**, so the endpoints the console depends on are enumerable in one place.

**A Platform form row names its control (console review C-003, beyond the auth forms).** `WS_FieldRow` (`ui/components/workspaces/shared.jsx`: the workspace provider and template forms) and `FieldRow` (`semantic-search.jsx`: the semantic-search provider forms) drew `<label class="field-label">` as a SIBLING of the input, with no `htmlFor` and no `id`, so a screen reader met unnamed edit fields and clicking a label focused nothing (72 fields). `FF_fieldControls` (`ui/components/shared/form-field.jsx`, inside `FormField`) gives the first native control among the row's direct children (`input`, `select`, `textarea`; its own `id` when it has one, else a `useId`-based one) the id the label points at, and an error (`err`) is `role="alert"` and tied to that control (`aria-invalid`, `aria-describedby`, merged with one it already has). A row whose control is a custom component or sits in a wrapper cannot be labelled by id, so the row is a `role="group"` named by its label (`aria-labelledby`). Only the first control of a row is labelled: a row with two inputs names the first. NOT done: the second control of a multi-control row (the hand-written `<label className="field-label">` sites elsewhere have the same defect and are counted by the ratchet in the next paragraph). (`tests/ui/test_form_rows_label_their_control.py` runs both components in V8, `tests/ui_e2e/test_form_rows_label_journey.py` the real template form.)

**One labelled form row, and a ratchet on the labels that name nothing (console review C-003, the rest of the console).** `FormField` (`ui/components/shared/form-field.jsx`; props `label`, `hint`, `help`, `err`, children, and `className`, `labelClassName`, `hintClassName` for a surface with its own look) is the console's one labelled row: `WS_FieldRow`, `FieldRow` and the console overlays' `NV_Field` are one-line wrappers of it, so the rule in the paragraph above has a single implementation, and a form draws `<FormField label="Name"><input /></FormField>` instead of a `<div className="field">` holding a bare label. The hand-drawn `<label className="field-label">` without `htmlFor` that remain are counted per file by `scripts/audit_field_labels.py` (a label that wraps its checkbox or input names it implicitly and is not counted; a comment that starts a line is skipped), and `tests/ui/test_field_label_ratchet.py` holds the count against `tests/ui/field_label_baseline.json`: a file may not have MORE than its baseline (a new bare label fails: use `FormField`) and may not have FEWER either, so the baseline is lowered with the conversion (`uv run python scripts/audit_field_labels.py --write`) and the gain cannot be given back later by a new bare label in the same file. The baseline started at 100 labels in 17 files (graphs 25, the harness form 11, workspaces 10, approvals 9, channels 8, the new-session form 7, internal collections 6, toolsets 6, then the rest); each surface converts in its own change and lowers its number. The scan also counts a `<div>` or `<span>` whose `className` literal carries `field-label` or `nv-field-label` (an element only styled as a label names nothing; the overlays' `NV_Field` was one and hid from the first version of the count), which adds 6 (workspaces 2: two block headings; agents 4: read-only value captions in the agent summary, which want a definition list rather than a field), so the baseline stands at 105 in 17 files after the overlay fix and the graph-input row. A class that merely contains the name (`field-label-row`) is another class, and a component handed `labelClassName="nv-field-label"` draws no such element itself. `help` is a muted line under the control (`field-help`) that describes it: the control's `aria-describedby` lists it before the error, and a row with no native control is a group described by it. **The console overlays** (`ui/components/console/nv-overlays.jsx`: New session, New agent and the rest) draw their fields with `NV_Field`, which was a `<div className="nv-field-label">` over the control, so none of them named its control and the count above never saw them; it is now `FormField` with the overlays' class names (`.nv-field-label` is `display: block` so the `<label>` lays out as the div did), the Name and Initial instructions fields are found by their label (a `hint` is a word of its own in the name, "Name optional": the row puts a space before it, and `.hint` / `.nv-field-hint` have a 3px margin for that space's width), and the fields around a custom widget (the agent/graph picker, the autonomy switch) are groups named by it. The graph-input rows of the New session overlay are `SharedNewSessionSchemaField` (`new-session-form.jsx`), now a `FormField` whose `help` is the schema's description (baseline 7 to 6). NOT done: the other conversions; the large `SharedNewSessionForm` in the same file has no consumer (nothing renders it) and keeps its other 6 bare labels until it is removed or converted; the mobile New session sheet (`nv-mobile-shell.jsx`) has a name input and an instructions textarea with a placeholder and no label; the count does not see a label with no `field-label` class, a class set by an expression, or a comment trailing code on the same line. (`tests/ui/test_form_rows_label_their_control.py` runs `FormField`, the three wrappers and the graph-input row in V8, `tests/ui_e2e/test_new_session_overlay_labels_journey.py` the real overlay; `tests/ui/test_field_label_ratchet.py` checks the scanner on synthetic JSX before it checks the tree.)

**The console has landmarks, a page heading and live regions.** On desktop the activity bar is `role="navigation"` named "Views", the topbar `role="banner"`, the rail `role="navigation"` named "Sessions and workspaces", the Files panel `role="complementary"` named "Files", and the shown view (`.nv-view`) is the one `role="main"`, headed by a visually hidden `h1.nv-sr-only` ("Studio", "Platform" or "System settings"; the overlays and pages keep their own `h1.page-title`). On a phone `.nv-mobile-shell` is the `main` landmark. The toast host draws two sibling live regions inside a stack that is not one itself (`nv-toasts-status`, polite `role="status"`, and `nv-toasts-alert`, assertive `role="alert"` for error toasts; an alert nested in a status region is announced twice by some screen readers). Because they are two regions, toasts of the two kinds are not interleaved in arrival order: within each region they are in arrival order, and the polite region is drawn above the assertive one. In the session document only the WORDS of the running status strip are a live region (`nv-status-live`, `role="status"`; `SH_statusWords`), the elapsed time beside it (`nv-status-clock`) is not, because a status region is atomic and the clock ticks every second; the reconnect note is `role="status"`. A pending approval card (`NV_DecisionCard`, prop `live`) and a failed turn's error card are `role="alert"` only when they ARRIVE while the document is open: `NV_useFirstLoadKeys` freezes the keys the first load of the history and of the pending gates brought (those are history and stay quiet, so opening a session with three past failures fires no announcement), and a card on a session that is over is never an alert (`ended`). The composer's accessible name is its current hint (`composerHint`: "Message <agent>...", "Steer mid-run ...", "Send to reopen this session..."), the same string as its placeholder, which changes with state and is not a name on its own, and the Platform list filters are named "Filter <page>". The streamed reply itself is not announced token by token; the status strip and the settled records are.

**An approval card's reject form says when it sends and can be folded (console review C-018).** `NV_DecisionCard` (`ui/components/console/nv-session-doc.jsx`) keeps one button for both steps: "Reject with feedback" at rest, whose first click only opens the reason box (focused, `aria-label="Reason for rejecting"`). Once open the same button reads "Send rejection" (red outline through `data-armed`, disabled until the reason has text) and `Cancel` (`nv-reject-cancel`) folds the form without a request and drops the draft, so the next open starts empty and its first click cannot send old text. Approve is never affected by an open form, and an ended session keeps the card read-only. (`tests/ui/test_decision_card_reject_form.py` runs the card in V8; the CI journey `tests/ui_e2e/test_approvals_journey.py` drives the same open, cancel, reopen cycle.)

**The session state chip says Ready for a session that merely rests.** The served `session_state` is coarse on purpose: `parked` covers every WAITING or PAUSED row that has completed a turn (`WorkspaceSession.session_state`), so labelling it by that word alone told the operator that every session that had simply answered was blocked. The header chip (`NV_SessionStateChip` in `nv-session-doc.jsx`) keeps `data-state` as served (the e2e journeys and tools read it) and decides the label from what the row stores, in `NV_sessionStateChipView`: a `parked_status` is a real park (an approval, an answer or a timer) and reads amber `Parked`, `status: paused` is the operator's pause and reads `Paused`, and any other row that rests reads `Ready` with `data-resting="true"`, drawn neutral. The richer per-reason wording ("Waiting on approval") is `describeSessionState` in `session-state.jsx`.

**A worker that has not reported its load is unknown, not idle.** `GET /v1/workers` rows and `/v1/health` serve `in_flight: null` for a worker from before load reporting, or one that has not yet sent a heartbeat with a load (#484). The Workers page (`workers.jsx`) keeps the null: a row reads "? / 3" and its bar is drawn dashed and empty with the title "Load not reported", the detail panel says "load not reported", the drain dialog says "its in-flight sessions" instead of a count (`WK_inFlightText`), and the "Running now" tile (`WK_fleetLoad`) sums only what was reported and reads "? / <slots>" with "1 worker not reporting its load" or "N workers not reporting their load" (`WK_unreportedText`) while any worker that can run something has not reported (dead workers are tombstones and count for nothing either way). The legacy health page charts nothing and prints "n/a" for an unreported total. The system dashboard already printed "n/a". Before this the page turned the missing number into 0, so an overloaded fleet of old workers read as idle.

**Stop is acknowledged.** `POST .../interrupt` returns before the turn has stopped, so the session document shows a "stopping" state until it has: `SH_isStopping(session)` (`ui/foundation/shell-status.js`) is true while the served `interrupt_requested` flag is set on a live session (the worker clears it when the Stop lands), and it is OR-ed with `stopPending`, the click's own state, so the button disables the instant it is pressed. While stopping, the composer's Stop and the status strip's interrupt button are disabled ("Stopping..."), and the strip says `stopping` (or `stopping: ending <tool>`: a Stop cancels a running tool, except one that must not be cancelled, such as a file write, which it waits for a few seconds, and the strip cannot tell which; `SH_stoppingLine`). Every entry point (the buttons, the `session.interrupt` palette verb, the rail's session menu) goes through `NV_doInterrupt`, which shares the pending request when pressed twice and toasts what actually happened: "Stopping the turn" only when the returned row carries `interrupt_requested: true`; "Nothing to stop: no turn is running" when the server answered 200 as a no-op (it does so on every row that is neither running nor parked: idle, waiting, paused, a turn that just finished), which also clears the click's pending state at once; and an ERROR toast with the request id on a failure. Every entry point is also gated on `SH_canStop(session)` (the server's own condition: a RUNNING row that is not parked): the composer's Stop and the strip's interrupt button render only for such a turn (or while one is stopping), the rail's session menu offers Interrupt only for it, and the `session.interrupt` verb is registered with an `available(ctx)` predicate that the palette's ranker applies to the focused session's row (`NV_focusedSessionRow`; the verb registry keeps `available` on its explicit whitelist, as it does `requiresLive`, which nothing evaluates yet). A Stop's `cancelled` record reads "stopped" in the transcript and a Cancel's reads "cancelled" (`SH_lifecycleLabel`). A pending click clears itself after 5 seconds if the served flag never appears, and the client's pending leg obeys the same parked/ended exclusions as the served flag (`stopPending && SH_canStop(session)`), so a parked row never reads "stopping". A PARKED session is never "stopping": no turn is running while it waits and the server refuses a Stop on it with 409, so the rail's session menu does not offer Interrupt for it, and a Stop that is refused anyway (from the palette verb, or a race) shows the server's reason in the failure toast and clears the click's pending state.

**A clean turn end says nothing; an unclean one says why (console review C-016).** The slim row that closes a turn (`NV_LifecycleRow`, `nv-turn:<seq>`) is the turn boundary and carries the turn's trace button (`nv-trace-open:<seq>`). `SH_lifecycleLabel` returns no label for a `done` that ended cleanly (`stop`, `stop_sequence`, `other`, or no reason), so the row draws the button alone instead of printing the record's name ("· done") after every answer. A `done` that did not end cleanly is named: `max_tokens` "cut off at the output limit", `content_filter` "blocked by the content filter", `error` "ended with an error", `tool_turn_cap` "stopped at the tool-turn cap". `yielded` and `resumed` still read "· yielded" and "· resumed", and a cancelled turn reads "stopped" or "cancelled". The trace button stays on the row because there is no other per-turn place for it yet; moving it onto the answer block would let a clean end draw no row at all. (`tests/ui/test_done_marker_row.py`; `tests/ui_e2e/test_trace_sidebar_journey.py` checks a real turn.)

**End, Park and Delete are reachable from every menu a session has, and each says what happened.** `NV_doPark`, `NV_doEnd` and `NV_doDelete` (`nv-session-doc.jsx`, exported on `window` for the rail) back the rail's right-click menu, the session header's overflow menu (the only menu a phone has) and the palette verbs `Park Session` (alias Pause) and `End Session` (alias Close; it was "Close Session" and has always been the hard cancel, never a tab close). Park is the pause route and asks nothing, since sending a message resumes the session; End asks first, naming the action on the button, because it cancels a running turn, and says a message sent later reopens the session; Delete confirms with a Delete button. Each resolves `{ok}`, `{cancelled}` or `{failed}` and never rejects: a success toasts, and a failure is one error toast carrying the server's own reason and the request id (deleting a running session answers 409 and used to show nothing while the turn kept running; a failed End also re-reads the row so a stale chip catches up). Park is gated on one predicate, `NV_canPark` (not for an ended or an already paused session), in the rail row, the overflow row and the palette verb, and End is offered only while the session is live; the rail's Delete refreshes the list but does not close an open tab for the session (the overflow's does); the header's own rename failure is the same shared toast. The header's overflow menu hides Split Right at the phone breakpoint (a phone has one pane). `End` joined the verb allowlist in `shell-verbs.js`.

**An idle session document polls slowly; anything in flight polls fast.** One open session that was doing nothing made about 110 requests a minute (the session row every 2 s, the pending yields and the external-tool banner every 5 s, the session list and the Files tree every 5 s, the workspace list twice every 15 s). `NV_sessionIsCalm` (`nv-session-doc.jsx`) says when the live tap and the refetch on its frames carry every change, so the polls only catch up: the tap is connected, no live status is showing, no send or Stop is waiting for the row, and the row says `turn_status: idle` with no interrupt, pause or cancel requested. The session row, the pending yields and the banner (`pollMs` prop of `ExternalPendingBanner`) then poll every `NV_CALM_POLL_MS` (15 s) instead of 2 to 5 s. The state is reached only after the session has been at rest for `NV_CALM_AFTER_MS` (5 s), because a turn's last frame can arrive before the row shows where the session came to rest, and it is dropped the moment anything stirs; a tap frame (`yielded`, `resumed`, `done`) also refetches the row, so a slow poll never delays one. While a session is calm, a change to its row that sends no tap frame (a rename, or the session ended from another client) takes up to 15 s to show; a frame, a Stop or a send brings the fast cadence back at once. The Files tree polls every 15 s instead of 5 s while no session of its workspace is running (`NV_anySessionRunning` over the shared session list), and the rail, the shell and the Files sidebar read that list through one hook, `NV_useSessionList`, so they cannot disagree about its cadence. The session list itself stays at 5 s on purpose: a session created elsewhere emits no tap frame, so the poll is how it appears in the rail. The shell and the rail used to fetch `GET /v1/workspaces` under two cache keys; it is one (`nv-workspaces`). A hidden tab already stops polling (`use-resource.js`), and the global idle mode still skips every poll that has not opted out. A measured idle session document (30 s, steady state, `tests/ui_e2e/test_idle_session_polling_journey.py`) makes about 27 requests where it made about 55.

**The running strip is the tap's word, checked against the row.** The strip's live status (`thinking`, a tool name) is held by the session store (`ui/foundation/session-store.js`) and comes only from tap frames: a user message or a tool call sets it, a terminal record (`done`, `cancelled`, `error`) clears it. A lost or never-written terminal frame would therefore leave "running" and a Queue button for good, so the session document also reads the polled session row, which is the truth about whether a turn is executing: when the row is ended or serves `turn_status` `idle` for `NV_STALE_STATUS_MS` (4 s, at least two polls of the 2 s detail resource) while a live status is showing, `NV_rowContradictsStatus` marks it stale and `SS_expireStatus` drops it and the document re-reads the durable tail. The `sending` leg of a message in flight is never expired, and a status a newer frame replaced is left alone. A send that fails gives back the status it replaced; it no longer re-arms `thinking`.

**A failed session says why, and a failed turn is one card.** The end divider (`session ended . <reason>`) gets a note under it from `NV_endedLine` (`nv-session-doc.jsx`): for a failed session the reason in user language and the next step (`ended_detail` `never_started` reads "It never started: the workspace or the agent could not be prepared."; a code the table does not know is shown rather than hidden; the snake_case codes a failed model call carries, `server_error`, `network_error`, `rate_limit`, `auth_error`, `stream_timeout`, `generation_timeout`, `context_overflow_unrecoverable`, `bad_request` and `connect_timeout`, read from one table, `NV_failureWords`, as a plain clause plus a next step specific to that failure), the same for workspace lost and the tool-turn cap, and nothing for the quiet endings (completed, cancelled, deleted). A failed stream writes its error with the cause and then a bare terminal marker (`{reason, terminal}`); `SA_toTranscript` (`session-adapter.jsx`) folds that marker into the cause written earlier in the same turn (a turn is what lies between two user messages), while a marker with no cause in its turn stays so the failure is never invisible. A model that dies mid-answer writes the stream's own Error row and then dispatch's ERROR record with the same message; the later copy from the same node is folded into the first, which carries the specific code. The same rule can fold a crash or reclaim marker into the retried attempt's failure when both carry the same words in one turn; that is accepted, since they say the same thing. The fold leans on the writers' order (the cause is written before its copies and its marker): a copy written before its cause would be the row kept, a marker that came first is removed when the cause arrives, and a row without a node id matches a cause of any node, so two graph nodes failing with the same words stay two cards only when both rows name their node. Parent and subagent failures never fold into each other (`SA_failureScope`: a delegated record carries `delegated` and `delegate_run_id`, or `delegate_tool_call_id` before runs had ids), because a subagent's row is drawn inside its own block and a parent turn that hit the same provider error would otherwise have no card of its own at the top level; a bare marker belongs to the scope that wrote it. The scope is the run id when the record has one, else the delegating call id, else a single shared `delegated` scope: two runs of one tool call stay two scopes, records written before either id existed all share the one, and a grandchild's failure (a subagent's own subagent) carries its own run id and draws in its own block. A non-fatal error (an explicit `fatal: false`: the provider reported a problem and the stream went on) is not a failure and is not folded: `SA_toTranscript` makes it a `retry_notice` row, never the cause a later failure folds into, and it is usually the first half of a failure: the agent loop holds a stream's first Error as the call's end and raises when the stream finishes, so dispatch writes its own ERROR with the SAME words (then the release marker), and a failure of the same scope (and node, as for copies) with the same words ABSORBS the notice, in either order and whatever output lies between them, leaving one red card (the failure keeps the notice's specific code when it has only the generic `/errors/internal`, since the code chooses the card's words) (the failure row, which is the one the server counts as the turn's end). A failure with other words, or in another turn or scope, leaves the notice. `NV_noticeView` draws it as a quiet line (`.nv-turn-note`, no alert role, no trace button) in one of three states settled by `SA_settleNotices` from the rows after it in the same turn and scope: `retrying` (amber: nothing followed yet), `recovered` (grey: output, or a done, followed) and `ended` (a failure card, a cancel or the next user message followed with no output). Output wins over a later ending, whatever came between. With the producer that exists today (the OpenResponses `error` event) `recovered` cannot happen: the loop fails the turn on ANY held Error, so the notice is always absorbed by dispatch's failure; the state is kept for an Error yielded after Done and for a loop that goes on (design ticket 01a11c07). A notice stays amber while live parts stream after it, because the live parts are not rows of the transcript yet and `retrying` is settled from the rows. A subagent's notice and a subagent's failure sit in its subagent's block, and `NV_subagentRows` draws both there (they carry no `label`, their words are in `payload.message`, so the label rule alone used to drop them and a subagent that failed showed nothing): the failure as the same red card with the same words (`NV_errorView`), the notice as the same quiet line (`NV_noticeView`), each under the subagent's name, neither announced as an alert (it arrives inside a block the reader may not be looking at; no `role`, no `aria-live`) and neither with a trace button (a trace belongs to the session's turn). The name is the delegating `system__invoke_agent` call's `arguments.agent_id`, because `DelegationRecorder` stamps no `agent_id` on the records it writes (a record that does carry one keeps it). The only producer of a non-fatal Error (the OpenResponses stream) makes the agent loop hold the Error, yield the Done first and the Error last, and raise, so the delegating call is answered with an ERROR result and the delegated scope gets NO failure record of its own for the notice to be absorbed by: a delegated notice whose delegating call FAILED and whose words the call's error output QUOTES is therefore drawn as the failure, the block's one red card, in the notice's words (`SH_callQuotesNotice`: a failed `invoke_agent` answers `{type, message}` with `subagent 'x' LLM stream failed: <the stream error's message>` and the resume path `{error}` with `subagent LLM stream failed: <the stream error's message>`, so the words END the text (read from `message`, else `error`, else the text itself; at a word boundary); the same words in the middle of an unrelated failure promote nothing; when a scope has several notices it is the LAST one the output quotes, so a call never shows two red cards, and a call that failed for a reason no notice names promotes none); a notice whose call has any other result never says the turn is continuing (the call is over, so a `retrying` notice reads as carried on); while the call is still running it is the quiet line in its own state. A call is paired with its result by RUN and scoped call id (`SH_nestWithResults`, `SH_resultForCall`: the key is the record's `delegate_run_id`, else `call:<delegating call id>`, else empty for the parent turn's own records, then `|` and the call id), with the index taken over the WHOLE transcript before nesting: the recorder writes a delegated run's tool results like any other row (`run_agent_turn` yields the call's `_ExecutorToolResult`, `run_subagent` feeds it to the recorder) and numbers scoped ids per run, so a child's call and its parent's are both `x:tool:1:1`; indexed by the id alone, and only at the top level, a nested call block showed its PARENT's result and a grandchild's notice read the parent's OK result ("carried on") or, with no collision, found none ("continuing") under a finished parent. A grandchild's failure is drawn in the CHILD's call block it belongs to. The record is still persisted as an `error` record; a record with no `fatal` flag and `fatal: true` are failures. The server does not count an ERROR with an explicit `fatal: false` as a turn end (`terminals.closes_turn`, ticket 01a11bf6), and neither does the console: a `retry_notice` row is no terminal to `SH_closesTurn` (nor is a raw error carrying the flag), so the ordinal asked of the trace is the server's. The same holds for the records the failure fold removes: the server counts the stream error, dispatch's copy and the release marker as three window ends, so the surviving failure row carries `foldedSeqs` (the SEQS of the copies and markers that were folded into it, never a subagent's; a marker written before its cause included) and `SH_turnOfSeq` steps the ordinal when its walk passes each of those seqs, not at the surviving row: a drawn row between a cause and a copy (a sibling graph node's answer, streamed text) belongs to a window the copy's end comes after. Before that, every turn after a failed one was numbered one or two too low and its trace asked for the wrong window; an earlier count at the surviving row's position then numbered those in-between rows too high. `NV_errorView` states the problem type, or the stream's snake_case code, in words ("The model provider had a server error.") and keeps the provider's own text below it as detail; a fatal stream error with no code at all reads "The model stopped answering part-way through." The header's context meter exists only when there is usage to show and is labelled for assistive tech, and on the mobile session screen the header title is hidden because the screen's top bar already names the session, and the header's overflow menu offers Rename so a phone keeps what click-to-rename gave the desktop.

**The open tabs survive a reload (console review C-023).** The URL names one document, so a reload used to keep one tab of three and lose a split's second group. `NV_Shell` now writes the tab groups' working set to `localStorage` under `primer.console.tabs.v1:<username>` (`TG_serialize` in `ui/foundation/tab-group-model.js`: each tab's kind and ref and whether it is a preview, each group's id and active tab, the focused group and the split direction; no names, results or content) and reads it back once at the next load (`TG_restoreInto`), merging the load's own model into it, so the URL's document is still the active tab and a document the link opened is focused rather than duplicated. The restore runs once under the key it read (`tabsKeyRef`) and the write only ever uses that key, so a visibility refetch of the auth status that turns out to be another user (a window shown again after someone else signed in) can neither store the tabs on screen under that user nor read theirs; the write also waits for the restore (`tabsRestored`) or the first render's one-tab model would overwrite what was stored. Two windows of one user share the key: the last writer wins. `TG_restore` trusts nothing it reads: a value that is not what `TG_serialize` wrote, or holds no usable tab, is no value; a tab of a kind the shell cannot open (`SH_DOC_KINDS`), without a usable ref (empty or over 1024 characters) or already open in another group is dropped; a second preview tab in a group is kept as an ordinary tab; the active tab, the focused group and the direction are repaired; a stored group id is reused only when it is a short plain token (at most 32 letters, digits, `_` and `-`) and is otherwise replaced; and the working set is bounded (6 groups, 60 tabs). Storage that throws (private mode, quota) is the same as an empty one. A restored tab whose session or file has since been deleted is the same as a link to it: whatever that shows, it is not special-cased here. Not done: a signed-out user's key is not cleared, and the set is per browser, not per account. (`tests/ui/test_tab_group_persistence.py`, `tests/ui_e2e/test_tab_groups_survive_reload_journey.py`.)

a list that holds a string (and any numbers, `null`s, objects or lists among the other words) is scrubbed as the command line it is, safe by construction: every word is its floor (what the member-by-member walk always showed for it, so a list is never worse than that walk) or the literal `<redacted>`, and never text derived from the other words. The ORIGINAL words are also joined with U+001F, which every rule sees as whitespace (a word with spaces and no quote is wrapped in single quotes for the line only, so `-u 'deploy:correct horse'` is one value; the quote characters of a word with no space are swapped for private-use stand-ins for the scan, so a `'` inside a secret does not end it; an object, list or JSON document is already walked and enters as one opaque word) and scrubbed once with a length-preserving mark (`_scrub_text(line, mark)` writes one mark for each character a rule hides, so where the marks fall says which word a rule found something in); a word with a mark on a character that its own text does not get alone is shown as `<redacted>`. So `["mysql", "-u", "root", "-phunter2"]`, `["curl", "-u", "admin:hunter2"]`, `["deploy", "--pass", "hunter2"]` and `["mysql", "-pS3cr3t!"]` hide their secret like the text forms do (the word the line found is `<redacted>`, the others stay; a header split into words, `["Authorization:", "Bearer", "x"]`, is three list members), and a script given to `sh -c` keeps its floor, the readable text with the secret replaced. The result is always a list, no shell parser touches a word and no text of the line is shown. The work is bounded by constants: at most 50 words, and only the words that fit in 2000 characters of line are taken (the rest are counted in `<N more>`), and everything handed to the scrubber (the floor's text, the word alone, the line) is charged to the walk's shared budget; a list of one, or with no string in it, is walked member by member (`tests/api/test_inbox_preview_argv_lists.py`, which holds the security review's probes and the differential property: for any list, every word is its floor or `<redacted>`); the false positives of the text rules apply to a list too (`--no-password db` and `--password-stdin registry` hide the word after them); this is shoulder-surfing protection, not access control (`Show all` and the session's own pending-yields route return the whole call) and a heuristic that errs towards hiding, with misses it keeps on purpose: a secret with no recognisable shape under a harmless name (`{"note": "correct horse battery staple"}`) a base64 secret under a harmless name that a `/` or `.` splits into runs of 32 characters or fewer (the blob rule matches an unbroken run of letters, digits and `+ _ = -`; adding `/` or `.` to it would redact the long paths an approver needs to read), the new rules' own misses (a `-p` or `-u` more than 32 words after the `mysql` command, a camelCase name such as `dbPASS` or an all-caps `DBPASS`, `-p` after any tool but the mysql family) and, accepted as false positives because hiding a harmless value costs a click on `Show all`, `find /var/lib/mysql -print`, `docker run --name mysql -p3306:3306 img` (a `-p` after a word that starts with `mysql`), `mysql -p$MYSQL_PWD`, `docker run -u root:root` and `pass: 12`; what the walker does not look at is hidden), every scrub pattern is linear (anchored starts and atomic groups; a quadratic one froze the server for minutes on 200 000 characters of the word `token`), an argument NAME is scrubbed like a value (a token used as a key shows as `<redacted>` in the line, in the nested JSON and in the rail's names; ## 5. Data model

The console's own data model is its URL grammar, which is the only thing it persists between loads:

```
#/w/{wid}?doc=<kind>:<ref>&overlay=<name>[:<section>[:<id>]]#<anchor>
```

The grammar also carries the view (`view=platform:<nav>` / `view=system:<nav>`; absent means studio, so every historical URL parses forward). Four doc kinds are addressable: `session`, `file`, `diff`, `wiki`. The overlay names are: `providers`, `collections`, `agents`, `graphs`, `triggers`, `toolsets`, `tools`, `workers`, `approvals`, `harnesses`, `services`, `channels`, `workspaces`, `new-session`, `new-workspace`, `internal-collections`, `activity` (the old `admin` overlay's sections are the System view's navs). An anchor is either `turn-<n>` or an `L<from>[-L<to>]` line range. Both lists are pinned against `ui/fixtures/shell/manifest.json` by a test, so the vocabulary cannot drift from what the designer package documents.

Beyond that, pages own no durable server data of their own. The entity schemas they render (Agent, Graph, Collection, Toolset, the provider models, WorkspaceSession, Trigger, ApiToken, and so on) are owned by their backend subsystem docs. The only page-held state is ephemeral React state: the active filter/sort/page, the selected row, the open-modal draft and its `fieldErrors` map, and per-page UI-only data such as the graph editor's `x/y` node coordinates (stripped before `PUT`). Cache keys are page-scoped strings on the foundation `useResource` map, listed per page above; they are an index into the shared cache, not a data model.

## 6. Lifecycle

**Boot is one gate.** `AuthGate` (`ui/components/auth.jsx`) owns the whole branch: register or login, the forced password change, the restricted screen, and the setup wizard for admins or the waiting screen for everyone else. It returns its children only once the install is complete, and its child is `NV_Shell`. `SetupWizardGate` is a LEAF that renders the wizard and never renders children, so it never appears in the mount chain; nesting the shell inside it would render the wizard forever. The shell used to carry a `setup_complete` branch of its own while both consoles coexisted, and it was removed with the flag day: two gates disagreeing about one decision is how a console strands itself. A FAILED read of `GET /v1/auth/status` is not a status: the gate shows what failed (`AUTH_failureView`: "Cannot reach the server" for a dead connection, which `apiFetch` reports as an `ApiError` with status 0; "The server is not ready" for a 5xx, "The server is busy" for a 408 or 429), retries on its own every few seconds after those (`AUTH_RETRY_MS`; the pending timer is cleared when the gate leaves the tree and when a click starts the next attempt), shows any other 4xx as an answer the server meant and does NOT poll it (it waits for the Try again button, which every failure screen offers), and never guesses that no account exists or that setup is incomplete (it used to, and offered to create the operator account on an install that has users). The wizard's own checklist (`SetupWizardGate` after step 2) never draws the setup state it read BEFORE the wizard ran: finishing step 2 clears the state, so the page says "Loading…" with Enter Primer off until the post-seed read arrives (it used to show a red "LLM provider responds: no LLM provider configured" for a moment right after the provider was configured), and a seed that FAILS still re-reads the state, so the checklist shows what is true with the failure banner and the row's Re-run seed instead of the stale read; the banner of a failed seed is titled "Couldn't run the setup seed", not "Couldn't load setup state" (that is the title of a failed READ), and a good re-run clears it (`tests/ui/test_setup_wizard_gate_mount.py` mounts the real gate in V8 with a scripted `apiFetch`; `tests/ui_e2e/test_setup_wizard_finish_checks_journey.py` drives it in a browser).

**The auth forms are labelled and their errors are announced.** `_PasswordField` (`ui/components/auth.jsx`) takes a required `id`: its `<label htmlFor>` points at the input (clicking the label focuses the field and a screen reader names it), its reveal button is named after the field it reveals (`Show password`, `Show current password`, `Show confirmation`) and reads `Hide ...` once revealed, and an input that has an error carries `aria-invalid` and `aria-describedby` pointing at its `field-err`. A `field-err` and the server banner (`auth-banner`) are `role="alert"` regions, so a failed submit is spoken. The username inputs of the register and sign-in forms follow the same rule. The password inputs on other surfaces (System > Users, the setup wizard's key field, the channel and trigger forms) are not changed by this. (`tests/ui/test_auth_password_field_a11y.py` runs the three forms in V8; `tests/ui_e2e/test_auth_form_accessibility_journey.py` finds the fields by label and reads the errors by role in a browser.)

**Every dialog takes focus, keeps it and gives it back.** `useFocusTrap(ref, active, opts, deps)` (`ui/foundation/focus-trap.js`, on `window.primerApi`) moves focus into the dialog when it opens (`opts.initial(node)` names the element, else the first focusable, else the node; focus already inside, such as an `autoFocus`'d input, is left alone), cycles Tab and Shift+Tab inside it, and on close returns focus to the element that had it when the dialog opened, if that element still exists. The opener is captured during render, not in the effect: React runs an `autoFocus` during commit, before any effect, so by then the opener is already lost. A handler that has already wrapped (a nested dialog) is not wrapped a second time (`defaultPrevented`). The shared `Modal` (every form modal, `confirmDialog`, `promptDialog`), the console's own overlay panel (`NV_OverlayPanel`: `role="dialog"`, `aria-modal`, named by its title through `aria-labelledby`, focus lands on the first field of its body, not on the close button) and the phone's `BottomSheet` (trapped only while `open`) all use it, so the Create session overlay no longer leaves focus on the "+" behind the scrim. Before this only `Modal` had a trap; the overlays and the sheet had none. Dialogs and sheets carry `aria-label` when their title is a string.

**Landing.** With a workspace resolved, the shell opens the most recent session as a pinned tab. An empty workspace creates one lazily, bound to the system default agent, so the console is never an empty frame asking what to do.

The dominant lifecycle inside an overlay is the CRUD-page round trip: the list bar mounts and its `useResource` poll loads the page of rows; the operator filters and clicks a row, which `navigate`s to the detail route; the detail page mounts, polls its own key, and renders the active `?tab=`; the operator opens the create/edit modal or a delete confirmation; on submit the `useMutation` fires the `POST`/`PUT`/`DELETE`, invalidates the relevant cache keys, and both surfaces refetch. Success pushes a toast; a 422 maps to inline field errors in the modal; a 409 cascade conflict renders inline inside the delete confirmation as a `Banner` so the operator can resolve the dependency.

```mermaid
sequenceDiagram
    participant Op as Operator
    participant L as List page
    participant R as Router
    participant D as Detail page
    participant M as Create/Edit modal
    participant API as /v1 (REST)

    Op->>L: open /x
    L->>API: useResource GET /v1/x?limit=200
    API-->>L: rows -> table / CardList
    Op->>L: filter (poll pauses on input focus)
    Op->>R: click row -> navigate(/x/:id)
    R->>D: mount SessionDetail/AgentDetail/...
    D->>API: useResource GET /v1/x/{id} (+ tab sub-resource)
    API-->>D: row -> header + active ?tab=
    Op->>M: Edit (modal reused with existing) / New X
    M->>API: POST or PUT-replace
    alt 200/201
        API-->>M: ok -> invalidate keys, refetch L+D, toast
    else 422
        API-->>M: ProblemDetails -> inline fieldErrors
    else 409 (delete cascade)
        API-->>D: conflict -> inline Banner in confirm modal
    end
```

Loader, empty, error, and confirmation conventions across pages: on first load a list shows a skeleton table (or simply renders zeros on metric boards); `loading=true` fires only on the first fetch for a key so background polls never flicker (a foundation guarantee). An empty result renders an entity-specific empty-state row or card with a "New X" call to action rather than a blank table. A fetch error retains the last good data (stale-while-error) and surfaces the error title; after three consecutive failures the poll halts until a manual Refresh. Destructive actions always go through a confirmation `Modal` whose body spells out consequences (in-flight counts, idempotency notes, the "second DELETE returns 404" caveat, the list of dependent rows for cascades) before the mutation fires.

A few pages run non-CRUD lifecycles. The session detail page reads the authoritative top-level `GET /v1/sessions/{id}` (never the nested workspace path, which is known to drift) and routes signals through the workspace-scoped POSTs; its five tabs are Overview, Messages, State, Files, and Turn log, and it additionally mounts a live stream panel fed by the workspace tap (an SSE `EventSource` on `GET /v1/workspaces/{wid}/tap`) plus the yielding-tool panels (AskUser, WatchFiles, Sleep, ApprovalBanner) and the `TurnLogTab` whose endpoint resolver picks the session route for agent bindings and the graph-run route for graph bindings. The internal-collections page derives one of three states (Inactive / Configured / Active) from a single config probe and drives a phase-aware bootstrap progress panel with adaptive 1s/5s polling. The graph detail page seeds an editable draft, auto-lays-out node coordinates, runs a client-side topology validator that gates Save, and issues a destructive `PUT`-replace.

## 7. Persistence

Pages persist nothing of their own to the server beyond the CRUD mutations enumerated above, and nothing to client storage. The small set of client-persisted preferences (theme, sidebar collapse state, the force-desktop opt-out) is owned by the foundation tweaks store and documented in [ui-foundation.md](ui-foundation.md). One historical client-persistence heuristic was deliberately removed: the internal-collections page once contemplated a `localStorage` "bootstrapped" flag, but the shipped page derives its state from the server-side `activated_at` field on the config row instead, so every client and operator sees the same truth. The `useResource` cache is in-memory and rebuilt from the API on every load.

## 8. Public surfaces

The public surface of this layer is the console's globals plus the page components it hosts. The console exports `window.NV_Shell` (the mount), `window.NV_OVERLAY_MOUNTS` and `window.NV_OVERLAY_TITLES` (the overlay table and its headings), and the `NV_*` surfaces each `nv-*.jsx` file attaches. The addressable vocabulary is `SH_DOC_KINDS` and `SH_OVERLAYS` in `ui/foundation/shell-url.js`.

Each page attaches `window.<Name>Page` and, for entities with a detail view, `window.<Name>Detail`; `ui/components/console/nv-overlays.jsx` is the sole dispatcher that maps an overlay target to one of those globals.

Cross-page exports that other pages depend on:

- `window.ApprovalBanner` (from `approvals.jsx`) is embedded by `session-detail.jsx`; both poll the same `tool-approval:session:{id}` cache key, so a respond from either surface refetches the other.
- `window.AG_NewAgentModal` (from `agents.jsx`) is launched inline from the new-graph dialog (`GR_NewGraphModal` in `graphs.jsx`) so an operator with no agents can create one without leaving the dialog.
- `window.WorkspaceTemplateCreateModal` (from `workspaces/templates.jsx`) is launched inline from the New-Workspace modal when no templates exist.
- The `workspaces/shared.jsx` form-helper widgets are exposed on `window.Workspace*` for reuse by the workspace, template, and provider modals.

Pages do not expose a programmatic API. A page navigates by calling `window.primerApi.useRouter().navigate(path, query)` exactly as before; the shim translates that into opening an overlay rather than changing a route.

## 9. Internal contracts

- **Detail pages carry their active tab in `?tab=`, read back through the router.** This makes tab state linkable and survives reload. Session detail uses `overview/messages/state/turnlog`-style ids; agents use `config/tools/sessions/metadata`; toolsets use `config/tools/sessions`; semantic-search uses `overview/config/collections`; workspaces use `files/sessions/log/channels/config/destroy`.

- **The create modal is the edit modal.** A non-null `existing` prop switches the submit from `POST` to `PUT`-replace, locks the id and type discriminator, and blanks masked-secret fields so the redaction is never round-tripped. Any page that edits an entity follows this, which is why there is no separate edit form to keep in sync.

- **Cache keys are page-scoped and mutations invalidate by key.** List and detail of the same entity use distinct keys (`sessions:list` versus `session-detail:{sid}`) so their independent poll cadences do not stall each other and a mutation can target exactly one surface. Shared keys are used deliberately where two surfaces must stay in lockstep (the tool-approval pending key, the IC config key shared by the sidebar bell, the knowledge OFF banner, and the dashboard tile).

- **422 maps to inline field errors; the loc-to-field mapping must match the backend emission.** Modals read `extensions.errors[].loc`, join it, and key inline errors by that path. Some backends flatten a segment out of the loc tuple (channel-provider config emits `body.{field}` not `body.config.{field}` because the model validator pre-instantiates the inner config), so the matching modal looks up the flattened key. Tool-approval validation forces a `body.*` loc prefix specifically so the approvals modal lights up.

- **409 cascade conflicts render inline in the delete confirmation, never as a bare toast.** Toolset delete blocked by an approval policy, SSP or provider delete referenced by a collection, workspace or template delete referenced by a child, and channel-provider delete all surface the conflict detail in a `Banner` inside the confirm modal so the operator can act on it.

- **Managed rows hide mutation.** Any entity carrying a `harness_id` (agents, toolsets, collections, documents, graphs) renders a "managed by harness" banner and hides the Edit button, mirroring the backend's 409-on-public-CRUD discipline.

- **Session detail pins the authoritative read path.** It always reads top-level `GET /v1/sessions/{id}` (and polls it), never the nested `/v1/workspaces/{wid}/sessions/{sid}` path, which is known to drift after signals; signals themselves still go through the workspace-scoped POSTs.

## 11. Historical decisions

- **Session detail pins the top-level `GET /v1/sessions/{id}` read for both initial fetch and polling, never the nested workspace path.** Why: the nested path drifts after pause/resume/cancel/steer (pinned by T0399/T0555/T0611) and the top-level row is the only authoritative view. Spec: docs/superpowers/specs/2026-05-16-ui-sessions-design.md.

- **List and detail of the same entity use separate `useResource` cache keys with separate poll cadences.** Why: detail is the action surface and polls faster (2s) while the list is a directory view that polls slower (3s to 5s); separate keys keep one from stalling the other and let mutations invalidate either independently. Spec: docs/superpowers/specs/2026-05-16-ui-sessions-design.md.

- **The create modal doubles as the edit modal across every CRUD page, with id/type locked and a `POST`-versus-`PUT`-replace switch.** Why: it avoids duplicating the form schema and the 422 field-error mapping between create and edit, and `PUT`-replace matches the storage-level full-replace contract. Spec: docs/superpowers/specs/2026-05-16-ui-providers-design.md.

- **Edit mode blanks any field still holding the `**********` secret redaction before submit.** Why: round-tripping the literal asterisks would clobber the stored secret; blanking lets the backend keep the existing value when the operator leaves the field untouched. Spec: docs/superpowers/specs/2026-05-25-designer-handoff-ui-spec.md.

- **The agent create form refuses a bad name and a missing description before it posts, and the agent status strip prints no developer line.** Why: `Bad Name!` was accepted as an agent id (`POST /v1/agents` answered 201, the model had no id pattern) and one press of Create on an empty form made a nameless agent whose description the form had replaced with "(no description)"; an id is permanent and sits in URLs and references, and a description is how OTHER agents find an agent (admin review 2026-10-08, ADM-14). The pure `AG_validateNewAgent(id, description)` (`agents.jsx`) returns refusals under the server's own field paths (`body.id`, `body.description`), so a client refusal and a server 422 share one display (the id field had none for a server error). The id is optional (the backend assigns `agent-<hex>`), but a typed one is lowercase letters, digits, hyphens and single underscores (two in a row are reserved for the agents a harness install mints, `<slug>__<template>`), starting with a letter or digit, at most 63 characters; surrounding spaces are dropped and a whitespace-only id is a blank one (it used to be sent as `"  "`, which the server then accepted); the description is required, on create AND on edit: clearing the description of an existing agent used to save the literal "(no description)", and what is sent is the trimmed description. An edit passes a blank id to the check (an existing agent's id is locked), so it can only be refused for its description. The backend enforces the same two rules on create (`primer/agent/agent_checks.py`, ticket 01a11c1c: a 422 at `body.id` or `body.description`, which this form's `fieldErrors` already displays; the system tools and the builder answer `validation-error`), and `tests/ui/test_agent_form_validation.py` fails when the form's regex and the backend's `AGENT_ID_PATTERN` differ or when the two disagree about an id; the client check stays so the person is told before the request goes. The status strip under "All references resolve" printed `GET /v1/agents/<id>/status · last checked just now · polled every 30s` (ADM-15: an endpoint and a poll interval, and "just now" was a fixed string); it now says "Checked automatically while this window is open" with the endpoint and interval in a tooltip. `tests/ui/test_agent_form_validation.py` runs the check in MiniRacer and pins how the form uses it; `tests/ui_e2e/test_agent_form_journey.py` drives the real form and the seeded operator's strip.

- **The new graph form stops inventing a description; a graph's description is optional, the form posts it trimmed, and the graph lists show a muted "No description" for an empty one.** Why: `GR_NewGraphModal` (`graphs.jsx`) used to post `description || "(no description)"`, the same placeholder ADM-14 removed from the agent form, so a graph created with the description field blank stored a fake sentence. The auth gate answers differently (review of #572): `require_user` raises `{"error": "auth_required"}` (401) and `{"error": "forbidden_role"}` (403) with NO message, so the problem's `detail` is the code itself and the code sits in `extensions.error`; the reader also reads that slot, treats a message equal to the code (or a snake_case `detail` with no code at all) as no sentence, and then says "Your session has ended; sign in again." or "Your role does not allow this." (`TR_BARE`) instead of printing the code or, on Fire now, regressing from main's "Authentication Failed"; a message that merely looks like a code is kept when the code is known and different, because a not-found message is a bare id and an id may hold an underscore. Every write error of the page goes through it, not only the four dialogs: Rotate token, Clear HMAC and the HMAC dialog (`TR_writeErrorText` delegates), the delete modal and the subscription panel (plain titles "Delete failed" and "Subscription update failed", the refusal text as the detail). The remedies were reworded in the review: a missing trigger says "Go back to the triggers list." (the pages that show it have no list to refresh), a refused cron says to check each field's range, because croniter takes 5 to 7 fields and aliases and what reaches the server has a bad value. `tests/ui/test_trigger_refusals.py` runs both in MiniRacer on the real messages and cross-checks the table against the codes `primer/api/routers/triggers.py` raises, so it cannot drift; `tests/ui/test_trigger_refusals_real_envelopes.py` answers the envelopes through the real error handlers, `require_user` and `_raise_code` (not hand-built dicts) and reads them with the real `ApiError`, for every fallback the dialogs pass; `tests/ui_e2e/test_trigger_refusals_journey.py` drives a duplicate slug and a Fire now on a deleted trigger against the real server. The fire-error CHIP (`TR_FireErrorChip`) is a different thing: it shows the code of an error the dispatcher RECORDED on the trigger, so it keeps its code.
- **The trigger subscription dialog's Kind, Target and Parallelism rows are named groups (console review C-003).** `TR_SubscriptionDialog` (`triggers.jsx`) had given its inputs an `id` and a `htmlFor` by hand; three rows sat under a bare `<label className="field-label">` that named nothing: `Kind` (a radio group, a locked value in edit mode), `Target` (the locked target of an existing subscription, edit mode only) and `Parallelism` (two radios). Each is a `FormField` (a `role="group"` named by its label, since no native control is its direct child); the baseline entry for `triggers.jsx` went from 3 to 0 (`tests/ui/test_trigger_subscription_form_labels.py`, `tests/ui_e2e/test_trigger_subscription_labels_journey.py`).

- **The minted plaintext API token is shown exactly once in a dedicated one-time dialog with a deliberate "I have saved it" close.** Why: the plaintext is the only secret (the backend stores a sha256 hash) and surfacing it only at `POST` with a forced copy step keeps the hash-only design intact. Spec: docs/superpowers/specs/2026-06-02-api-tokens-bearer-auth-design.md.

- **System > Profile says a wrong current password in words, and its empty states describe what is there.** Why: `POST /v1/auth/change-password` answers a wrong current password with 401 and the code `invalid_credentials` (the problem envelope's `detail`, repeated in `extensions.error`), and the page printed `err.detail` as it came (admin review 2026-10-08, ADM-25). The pure `NV_passwordChangeMessage` (`nv-system.jsx`) maps the CODE, not the status, to "The current password is not right." with the single-sign-on case named, because the same 401 also answers an account with no password and a lost race with another change, while an expired session answers 401 with another detail and keeps the server's own words; a bare machine code that is not known is never shown as the sentence. The Linked accounts empty state said "Link a single sign-on provider below" when no provider is configured and there is nothing below (ADM-27): the pure `LA_emptyHint(providers, loaded)` says where an administrator adds one (System > SSO), says nothing until the providers read has answered (they load separately, so no flash), and a FAILED read leaves them unknown, so an outage is never reported as "none configured". The API tokens empty state no longer repeats the header's "Create token" button. `tests/ui/test_profile_page_messages.py` runs the two helpers in MiniRacer and pins how the components use them; `tests/ui_e2e/test_profile_page_journey.py` drives the real wrong-password request with the three list reads stubbed.

- **AskUser input errors render inline under the input while action outcomes use toasts.** Why: input validation belongs next to the field the operator is editing, whereas an action's success or failure is a transient acknowledgement; the WatchFiles/Sleep cancels and the SSP create/delete use the inverse split deliberately. Spec: docs/superpowers/specs/2026-05-24-ui-semantic-search-and-yielding-tools-design.md.

- **The web-search and MCP-server pages reuse the list-bar plus stacked-panel shape with a reserved built-in row rendered inert.** Why: the bootstrapped DuckDuckGo web-search row and the MCP exposure singleton are server-owned, so they render with a built-in badge and no Edit/Delete affordance rather than being hidden. Spec: docs/superpowers/specs/2026-06-03-web-search-providers-design.md.

- **Both predecessor consoles were deleted together on flag day, not phased out.** Why: a half-deleted console is worse than either of them alone, because a stale route silently wins and nobody can tell which surface they are looking at. The deletion is pinned by a grep-clean gate rather than by intent.

- **`primerApi.useRouter` survived the deletion of the router.** Why: eight re-hosted page components read `params.id` or call `navigate`, and deleting the name would have broken every one of them the moment its overlay opened. The shim publishes the same contract over overlay state, so the pages did not have to change at all.

- **The console has no page-level chrome, so the toast stack and the confirm host moved into the shell root.** Why: both are cross-cutting. `window.primerApi.toastPush` is what non-React callers such as `useMutation` use to report a failed write, and a queue nothing renders swallows exactly the errors an operator needs to see.

- **The default workspace never overrides a navigation (ticket 01a11d41, the unknown-workspace CI flake).** Why: the shell's default-workspace effect (`if` the list is loaded, pick the first workspace) runs after the render in which the list arrived, and the closure it ran with held that render's `wid` (null). A link followed between the render and the effect had already queued `setWid(<the link's workspace>)` through the hashchange listener, and the effect's plain `setWid(first)` from the stale closure queued after it and won: the link's workspace was lost, its `doc=` kept, and the URL write effect wrote the first workspace into the address bar (a test that navigated right after `domcontentloaded` ended on the first workspace and never saw the not-found card, about one run in thirty in CI). The pick is now a functional update (`setWid(function (current) { return current || wsItems[0].id; })`): it sees the latest value and only fills an empty one. Pinned by `tests/ui_e2e/test_shell_default_workspace_keeps_a_navigation_journey.py`, which puts the navigation INSIDE the window on purpose (an init script wraps `React.useEffect` and lands the hashchange just before that effect runs: 6 of 6 runs lose the navigation on the old code) and a source pin in `tests/ui/test_shell_url_write_reads_first.py`.
- **The shell reads the address bar before it writes it.** Why: the URL write effect runs after the first render, so a hash that changed between that render and the effects (a link followed while the console boots, or a test that sets `location.hash` right after `goto`) was overwritten with the URL of the stale first-render state before its event could be read, and the navigation was lost for good (the ui-e2e flake on the `channels/rules` and `providers/*` routes). `nv-shell.jsx` keeps the address bar it last read or wrote in `ownHashRef`; when the bar differs from both that and the state's URL, the write effect calls the listener's reader (`readUrlRef`) and writes nothing, so the navigation is applied and the state, not the bar, gives way. Pinned by `tests/ui_e2e/test_shell_reads_an_early_hash_change_journey.py` (the hash moves the instant the shell registers its listener, silently and with an event) and the source pins in `tests/ui/test_shell_url_write_reads_first.py`.
- **The address bar shows what the console applied, not what a link said (console review C-025).** Why: the parser drops what the grammar does not know (an overlay or view section outside it, a doc of an unknown kind, a path that is not `/w/<id>`, any other parameter) but the write effect only runs when a state value moved, so junk that parsed to the state the console was already in (`?overlay=bogus`, `?view=bogus`, `?foo=bar`) changed nothing and stayed in the bar, and a shared link carried a parameter that meant nothing. The hash listener (`onNav` in `nv-shell.jsx`) now replaces the bar with `SH_buildUrl(parsed)` whenever that differs from the hash it read (`replaceState`, never a push, and `ownHashRef` follows), so a valid link, which is its own canonical form, is left byte-identical and one with an unknown part loses it. The canonical form is built from what the link PARSED to, not from the live state, so a link naming no doc does not get the open doc written into it. A reordered or over-escaped link is rewritten to the builder's order and escaping, which is the same address. Pinned by `tests/ui_e2e/test_shell_url_normalises_junk_journey.py` (nine junk shapes, a path outside the grammar, a valid link left alone).

- **A refused webhook-secret write says why.** Why: the server refuses a PUT or a `rotate_token` on a webhook trigger by anyone but its owner or an admin (403 `forbidden_role`, whose `detail` states the rule); the trigger detail page's Clear HMAC swallowed the error, so the secret stayed and nothing said so, and Rotate token and the Set HMAC dialog printed only the title, "Forbidden". `TR_writeErrorText(err, fallback)` in `triggers.jsx` picks the server's `detail` first, then the title, then the fallback, and all three use it; Clear shows the text inline beside its button (`hmac-error`, `role="alert"`), as Rotate token does. A new attempt, and a successful Set, clear a refusal that is no longer true. Pinned by `tests/ui/test_trigger_write_errors.py` and `tests/ui_e2e/test_trigger_secret_refusal_journey.py` (the 403 is answered by the test: auth is off in the ui-e2e lane).

**A failed `ask_user` call is a failed tool call, not an answer.** `NV_toolCallElement` (`nv-session-doc.jsx`) draws an `ask_user` call that has a result as the answered card (`NV_AnsweredAskCard`: the question and the operator's answer, or "Timed out" or "Cancelled", which the tool returns on purpose with `error` false) only when the result is not flagged `error`. A call that failed (for example the model gave a wrong argument name and the result is the tool's validation error) goes to the ordinary tool block, which carries the "failed" tag every failed call has, instead of a green "Resolved" card showing the raw error JSON as the answer (console review C-013). A still-pending `ask_user` call has no result yet and is drawn by the live attention surface, as before.
